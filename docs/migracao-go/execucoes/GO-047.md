### Decisões de escopo (preflight)

1. **Fonte de verdade do legado**: `packages/server/app.js` (lib npm `i18n`, catálogo estático `locales/<locale>.json`, ~36 idiomas em `models/config.ts:available_languages`), `packages/server/routes/utils.ts` (`setLanguage`/`applyUserLocale` — prioridade `User.language` > cookie `lang` > `default_locale` da config do tenant; detecção de RTL para `ar/he/fa/ur/yi`), `packages/server/routes/infoarch.ts` (`/localizer/*` — CRUD de idiomas HABILITADOS por tenant + strings customizadas traduzidas, e `/localizer/translate-llm/:lang`, a tradução assistida por LLM).
2. **Achado real: o catálogo de ~36 idiomas + `/localizer` (CRUD de idiomas/strings + tradução LLM) é uma superfície de PRODUTO muito maior que o "Aceite" desta task exige.** O aceite fala em "pelo menos 2 idiomas configuráveis por tenant, com seleção por usuário persistida" — não em replicar as 36 opções nem a UI administrativa de tradução assistida por LLM (que também exigiria uma integração de LLM que este backend Go não tem hoje, nenhuma task anterior configurou isso). Decisão: portar o MECANISMO (resolução de idioma efetivo, seleção por usuário, catálogo de strings de UI, RTL) com exatamente 2 idiomas reais (pt/en — pt porque é o idioma em que todo o código deste port já foi escrito desde o início, ver comentário de escopo abaixo), e não a UI de administração de idiomas/strings custom (`/localizer`) nem a tradução assistida por LLM. Ambas ficam documentadas como fora de escopo, não esquecidas — candidatas a uma task própria se/quando o produto precisar de mais de 2 idiomas ou de tradução assistida.
3. **`saltcorn dev translate` (tradução assistida por LLM) — decisão explícita, fora de escopo.** Exigido pelo enunciado da task ("decidir explicitamente... com justificativa"). Motivo: (a) nenhuma integração de LLM existe no backend Go hoje — seria uma capacidade nova e maior, não uma extensão de i18n; (b) o catálogo de strings desta entrega é pequeno o bastante (levantamento manual de TODOS os componentes de produto real do frontend React — App.tsx/EditorPage.tsx são páginas de demonstração/dev, documentado nos próprios arquivos, não contam) para tradução manual direta, sem precisar de assistência automatizada.
4. **Idioma "nativo" deste port é português — decisão que orienta o design de chaves.** Todo comentário/string deste stack novo já foi escrito em português desde GO-018 (não uma escolha desta task). As chaves de tradução são SEMÂNTICAS (ex.: `"views.loading"`), nunca a própria string em português como chave (evitaria colisão por pontuação/espaço e tornaria refatoração de texto uma mudança de API) — cada chave tem uma entrada `pt` e uma `en` explícitas no dicionário.
5. **Levantamento real das strings de produto (não-demo) do frontend React** — `App.tsx`/`EditorPage.tsx` são páginas de demonstração/dev, documentado no PRÓPRIO comentário de cada arquivo ("não é uma rota real do produto") desde GO-018/019 — não são alvo de tradução. As únicas superfícies de produto real hoje: `Topbar.tsx` (2 aria-label), `ListView.tsx`/`ShowView.tsx`/`EditView.tsx` (render de views reais, GO-020/039), `ViewsListPage.tsx` (página administrativa real, GO-020/039) — ~20 strings ao todo, catalogadas e traduzidas nesta entrega.
6. **Persistência**: `identity.User.Language` (novo campo, mesmo nome/semântica do `User.language` do legado) para a preferência EXPLÍCITA do usuário; `internal/config` (GO-027, já existe, genérico key/value) para `default_locale` do tenant — nenhum schema novo necessário para o tenant, só uma chave nova. Prioridade de resolução do idioma efetivo: `User.Language` (se setado) → cookie `lang` (BFF) → `default_locale` do tenant → `"pt"` — mesma ordem do legado (`setLanguage`/`applyUserLocale`).
7. **RTL**: mesma lista do legado (`ar`, `he`, `fa`, `ur`, `yi`) — nenhum dos dois idiomas desta entrega (pt/en) é RTL, mas o mecanismo de detecção é portado (não hardcoded para "sempre LTR") para não precisar de retrabalho quando um idioma RTL for adicionado.

### Achados reais encontrados durante a execução (não previstos no preflight)

**1. Achado de ISOLAMENTO DE TESTE (não do produto): o harness E2E compartilha o mesmo usuário/tenant entre Chromium e Firefox.** `run.sh` semeia UMA sessão (`cli e2e-seed`) reaproveitada por TODOS os specs/navegadores da suíte. Como a preferência de idioma agora é PERSISTENTE por usuário (`identity.User.Language`), o novo `i18n.spec.ts` — ao trocar para "en" no Chromium — vazava esse valor para a execução seguinte no Firefox (mesma sessão), que esperava encontrar o estado inicial "pt". Corrigido limpando a preferência via `PATCH /api/bff/actor/language` explicitamente ANTES e DEPOIS do teste (nunca confiando em um estado inicial implícito). Um segundo achado do mesmo tipo: `getByText("publicada")`/`getByRole("button", {name: "Visualizar"})` colidiam (`strict mode violation`) com views de execuções ANTERIORES do mesmo spec (a fixture HTTP nunca remove tabelas/views antigas) — corrigido escopando as buscas à linha da tabela (`getByRole("row", {name: ...})`) em vez de buscar por texto genérico na página inteira.
**2. `cli e2e-seed`/fixtures de teste HTTP faltando `config.EnsureSchema`.** Mesma classe de achado já vista em GO-040 (`triggers.EnsureSchema`) e GO-045 (`outbox.EnsureSchema`): `getActorHandler` agora consulta `_sc_config` (chave `default_locale`) em TODA chamada — corrigido em `cmd/cli/e2eseed.go` e nas fixtures de teste HTTP de `cmd/server` (`newTestFixture`/`newVersionedFixture`). O caminho de provisionamento real (`internal/installation/migrate.go`) já incluía `config.EnsureSchema` desde GO-027 — só os atalhos de bootstrap de teste/E2E ficaram para trás, mesmo padrão dos achados anteriores.

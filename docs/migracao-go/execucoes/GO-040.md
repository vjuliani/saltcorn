### Decisões de escopo (preflight)

1. **Achado real: `updateRecordHandler`/`deleteRecordHandler` não existem em `cmd/server`.** A descrição original da task presumia que os três handlers já existiam com `hooks=nil` — só `createRecordHandler` existe (confirmado por `grep` em `cmd/server/records.go`). `internal/records.UpdateRecord`/`DeleteRecord` (GO-013) já existem como funções Go, só nunca foram expostas via HTTP. Em escopo: adicionar as duas rotas, generalizando o padrão já usado por `createRecordHandler` (idempotência via `outbox.Do`, `_version` obrigatório para update, `?version=` para delete — mesma convenção já usada em `deleteViewRowHandler`, GO-039).
2. **Carve-out para GO-052: mecanismo de evento nomeado (`Trigger.emitEvent`).** O trigger real do pack `guitars` (`receive_share_trigger`) usa `when_trigger: "ReceiveMobileShareData"` — confirmado lendo `packages/server/routes/api.ts` do legado: é um evento NOMEADO genérico, emitido via `POST /api/emit-event` (`Trigger.emitEvent(eventname, channel, user, payload)`), com um modelo de autorização próprio (`ReceiveMobileShareData` sempre permitido para usuário autenticado; outros nomes exigem `mobile_emit_allowed_events` configurado) — inteiramente DESACOPLADO de qualquer escrita de registro. `internal/triggers.WhenTrigger` (GO-024) é um conjunto FECHADO (`Validate`/`Insert`/`Update`/`Delete`), atado aos hooks de `internal/records` — não existe hoje nenhum canal para um evento arbitrário disparar um trigger. Estender isso corretamente (nomes arbitrários, rota HTTP de emissão, modelo de autorização por nome de evento) é uma capacidade nova e maior, não uma extensão mecânica do wiring de hooks desta task. Fora de escopo, registrado como GO-052.
3. **Carve-out para GO-052: capacidade de ESCRITA em `internal/pluginhost`.** Mesmo que o mecanismo de evento nomeado existisse, o código JS real do trigger (`Table.findOne({name: "photos"}).insertRow(...)`) faz ESCRITA via um singleton de domínio (`Table`) — `internal/pluginhost` (GO-022) deliberadamente só expõe `CapDBRead` (leitura) e nunca singletons como `Table`/`File`/`View` (decisão já registrada em `docs/migracao-go/execucoes/GO-022.md`, nota 5: "escrita a partir de expressão/plugin... precisa de decisão própria de idempotência"). Adicionar uma capacidade de escrita — com sua própria política de idempotência e autorização — é uma decisão de design própria, não desta task. Fora de escopo, mesma task GO-052.
4. **Em escopo: `run_js_code` com o contrato de LEITURA já existente.** A ação nativa `run_js_code` (deliberadamente deferida em GO-029) é portada nesta task, roteando para `internal/pluginhost.Client.Eval` com `Kind: KindExpr`, contexto `{Row, User}`, e `Capabilities: [CapDBRead]` — o mesmo contrato que `internal/expression.Evaluator` (GO-023) já usa para condições `only_if`. Isso torna QUALQUER trigger Insert/Update/Delete/Validate com uma ação `run_js_code` de leitura funcional de ponta a ponta — só não o trigger ESPECÍFICO do pack guitars, que precisa de escrita (item 3).
5. **Em escopo: consumidor real do outbox de triggers `AfterCommit` no `cmd/worker`.** `Dispatcher.enqueueAfterCommit` (GO-024) já grava um evento `_sc_outbox` do tipo `"trigger:<ação>"` de forma durável — mas o fallback do `notify.Handler` em `cmd/worker/main.go` só LOGA qualquer evento que não seja email/webhook ("demonstração, sem consumidor real ainda"). Sem isto, um trigger `AfterCommit` nunca executa sua ação de verdade — um gap real, dentro do escopo natural desta task ("triggers/ações... na mesma transação/outbox", aceite original).
6. **Ciclo de vida do host de plugins em `cmd/server`:** um único `*pluginhost.Client` por processo `cmd/server` (mesmo padrão de único cliente de longa duração que `internal/pluginhost` já pressupõe, GO-022), iniciado sob demanda (lazy — só o primeiro `Eval` sobe o processo Node, evitando custo de warm-up quando nenhum trigger usa `run_js_code`) e fechado no shutdown gracioso (`shutdown.Tracker`, mesmo mecanismo já usado por todo o resto do servidor).

- **Nota de escopo (decisão de design):**
  - **Controle de versão** (escopo explícito da tarefa) é implementado via a coluna de sistema `xmin` do Postgres (o identificador de transação que gravou a versão atual da linha) — não uma coluna `version`/`_version` própria adicionada ao schema de GO-011 (que já está mergeado e testado; evitar tocar nele sem necessidade). `UpdateRecord`/`DeleteRecord` exigem o `xmin` lido numa consulta anterior (`expectedVersion`) e falham com `ErrVersionConflict` se a linha mudou desde então — controle de concorrência otimista real, usando um mecanismo que o Postgres já garante, não fabricado. `Compile` (GO-012) passa a incluir `_version` (`xmin::text`) em todo resultado, para que uma leitura sempre entregue o token necessário para uma escrita subsequente.
  - **Pontos de extensão de triggers** (escopo explícito) são um `Hooks` struct com callbacks `Before{Insert,Update,Delete}`/`After{Insert,Update,Delete}`, chamados DENTRO da mesma transação do comando — um hook que falha desfaz a operação inteira (mesma transação). Nenhuma automação real usa isto ainda (GO-024/025 não existem) — é o ponto de plugue testável, mesmo espírito do `metadata.Cache` sem consumidor real (GO-011).
  - **Autorização** é só em nível de tabela (`identity.CanWrite(actorRole, table.MinRoleWrite)`) — autorização por ownership de linha (`identity.IsOwnerByField`, GO-008) exigiria o catálogo de GO-011 saber qual campo é o "campo de ownership" de uma tabela, o que não existe hoje; documentado como lacuna explícita, não fabricado.
  - Erros do driver Postgres são classificados (violação de unicidade → `ErrDuplicateValue`; violação de FK → `ErrInvalidReference`; NOT NULL → `ErrRequiredField`) — nunca a mensagem crua do driver propagada como está (mesma disciplina de GO-010/011 sobre não vazar detalhe de linha em mensagens de erro).

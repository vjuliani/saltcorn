## Preflight — levantamento e decisões de escopo

Pesquisa dedicada (subagente, leitura do legado + Go) cobrindo: (1) `Trigger.emitEvent`/`POST /api/emit-event` do legado (`packages/saltcorn-data/models/trigger.ts`, `packages/server/routes/api.ts`); (2) a configuração exata de `receive_share_trigger` no pack piloto `guitars` (extraída de `deploy/playwright_mobile/backups/guitars_backup.zip`); (3) as duas notas de carve-out de GO-040; (4) o modelo de capacidade atual de `internal/pluginhost`; (5) o modelo atual de `internal/triggers.WhenTrigger`/`Dispatcher`.

**Achados centrais:**

1. `Trigger.emitEvent(eventname, channel, user, payload)` busca triggers por `when_trigger === eventname` — SEM exigir tabela (`Trigger.find({when_trigger: eventType})`, sem `table_id`). A rota `POST /api/emit-event/:eventname` distingue autorização: `"ReceiveMobileShareData"` sempre permitido para ator autenticado; qualquer outro nome exige a config `mobile_emit_allowed_events` (array); usuário público (não autenticado) tem uma config SEPARADA, `mobile_emit_public_events`.
2. `receive_share_trigger` real do pack: `when_trigger: "ReceiveMobileShareData"`, `action: "run_js_code"`, `configuration.code`:
   ```js
   if (Array.isArray(row.files) && row.files.length) {
     const photos = Table.findOne({ name: "photos" });
     for (const file of row.files) {
       await photos.insertRow({ photo: file.location, inserted_at: new Date() });
     }
   }
   ```
   Confirma: `Table.findOne` é chamado SEM `await` (síncrono no legado — resolve contra um cache em-memória), só `.insertRow` é `await`ado (I/O de verdade).
3. `docs/migracao-go/execucoes/GO-040.md` já registrava os dois carve-outs literalmente: (a) "`internal/triggers.WhenTrigger` (GO-024) é um conjunto FECHADO... não existe hoje nenhum canal para um evento arbitrário disparar um trigger"; (b) "`internal/pluginhost` (GO-022) deliberadamente só expõe `CapDBRead`... Adicionar uma capacidade de escrita — com sua própria política de idempotência e autorização — é uma decisão de design própria, não desta task."
4. `internal/pluginhost.Capability`/`Client.Eval` já são genéricos por nome — uma capability nova não exige mudança de protocolo, só um novo callback registrado pelo chamador.
5. `_sc_triggers.table_id` é `NOT NULL` hoje — bloqueia fisicamente um trigger sem tabela, mesmo problema (motivo inverso) já visto em `_sc_workflows` (GO-048) não reaproveitar `_sc_triggers`.

**Decisões de escopo tomadas no preflight:**

- **`table_id` nullable no MESMO catálogo `_sc_triggers`** (não uma tabela paralela) — o formato de linha é idêntico entre trigger de registro e trigger de evento nomeado, só a obrigatoriedade de `table_id` muda.
- **Validação cruzada em `CreateTrigger`**: `TableID != 0` exige um dos 4 `WhenTrigger` reservados; `TableID == 0` exige um nome que NÃO seja um desses 4 — evita um trigger que nenhuma das duas consultas de despacho (`TriggersFor`/`TriggersForEvent`) jamais encontraria.
- **`mobile_emit_public_events` (usuário público) fica FORA de escopo, não por preguiça — não há chamador para exercitá-lo**: `tenancy.Middleware` sempre exige uma identidade delegada verificada; não existe, nesta arquitetura, um caminho de requisição HTTP genuinamente anônima chegando ao Go (o BFF resolve sessão de navegador ANTES de delegar).
- **`channel` do legado (filtro secundário/pub-sub, também reaproveitado para cron/tabela) fica fora** — nenhum uso real desta entrega precisa dele (`receive_share_trigger` usa `channel: null`); inventar suporte sem um segundo caso real seria especulativo.
- **`actorRole` deve propagar sem elevação** até o callback de escrita — exigiu estender `Dispatcher.RunOne`/`HooksFor`/`RunJSCodeFunc` (e, para o caminho AfterCommit pré-existente, o próprio payload do outbox) com um parâmetro novo, tocando também o caminho de escrita de registro comum (não só o novo mecanismo de evento).
- **Idempotência da escrita não é um mecanismo novo dentro do host** — herdada do chamador HTTP (`Idempotency-Key`/`outbox.Do` envolvendo a emissão INTEIRA), mesmo padrão já usado por `submitView`/`runWorkflow`.
- **Capacidade de escrita (`db.write`) concedida SÓ a `run_js_code`**, nunca à avaliação de expressão genérica (`only_if`, campos calculados) — preserva o princípio de GO-023 de que a fórmula de um USUÁRIO nunca tem efeito colateral; `run_js_code` é uma ação mais privilegiada por natureza (configurada por um admin).
- **`Table.findOne` só aceita `{name: string}`, síncrono, sem RPC** — só `insertRow` (o único método real usado pelo pack piloto) chama `db.write`; `updateRow`/`deleteRows`/`getRows` continuam indisponíveis, `File`/`View` continuam totalmente bloqueados.

### Achados reais corrigidos durante a execução (não são bugs de produto do motor em si)

1. **Nenhum harness de E2E anterior exercitava `run_js_code`/o host de plugins de verdade**: `migracao/e2e/run.sh` nunca compilava `migracao/packages/pluginhost` nem definia `SALTCORN_GO_PLUGINHOST_SCRIPT`, e `cli e2e-seed` nunca concedia ownership de `plugins.expr` (`internal/pluginhost.ExpressionCapability`) para o tenant de E2E. Confirmado por evidência de falha genuína ANTES da correção: um smoke test manual (servidor real + tenant seedado, fora do Playwright) devolvia `ErrUnknownAction` sem `PLUGINHOST_SCRIPT`, e teria devolvido `expression.ErrLegacyOwner` mesmo com o script configurado, sem `plugins.expr` OwnerGo. Corrigido nos dois pontos; o mesmo smoke test, depois, disparou `receive_share_trigger` de verdade e gravou 2 linhas reais em `e2e_seed_photos` (uma por arquivo em `row.files`), confirmado por consulta direta ao Postgres.
2. **Ausência de rota HTTP para ADMINISTRAR triggers**: nem esta task nem nenhuma anterior (GO-024/029/040) jamais construiu um CRUD HTTP para `_sc_triggers` — só o mecanismo de DISPARO existe. Um harness de E2E dirigido pelo navegador não tem como criar o fixture de `receive_share_trigger` por conta própria (ao contrário de tabelas/views, que todo spec anterior cria via `/api/bff/tables`/`/api/bff/views`). Resolvido semeando o fixture diretamente via Go dentro de `cli e2e-seed`, mesmo mecanismo e mesma justificativa (bootstrap anterior a qualquer requisição autenticada) já usado para o usuário admin.
3. **`records.CreateRecordTx` devolve o registro criado (um mapa), não `nil`**: um teste inicial do callback de escrita usava `Table.findOne(...).insertRow(...)` como a ÚLTIMA expressão do código JS (sem descartar o retorno) — como `run_js_code` sempre coage o resultado para `FieldBoolean` (efeito colateral, resultado descartado por contrato, ver comentário de `runjscode.go`), o mapa devolvido por `insertRow` falhava a coerção (`tipo map[string]interface{} não suportado para boolean`). Corrigido no teste (`, true` ao final, descartando o valor explicitamente) — não uma mudança de comportamento do produto, um lembrete de que `run_js_code` sempre exige um valor final coagível (já documentado, agora com um caso concreto que o exercita).

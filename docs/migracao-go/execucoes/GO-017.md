### Nota de escopo (decisões de design, registradas antes de codificar)

Esta tarefa tem uma superfície muito maior que as anteriores — cria um pacote inteiro em outro runtime — então as decisões abaixo são fixadas ANTES da implementação, não descobertas ad-hoc, para evitar invenção de escopo no meio do caminho.

1. **Lacuna real descoberta: `internal-api.yaml` (GO-006) nunca foi implementado em `cmd/server`.** Só existe a rota de exemplo/placeholder (`tenantProbeHandler`, um `SELECT now()`, sem tabela de domínio real). `internal/records` (GO-012/013) tem toda a lógica de domínio pronta, mas nenhum caminho HTTP a expõe. Sem isso, "Contratos React–BFF–Go passam integração" (critério de aceite desta tarefa) não é verificável — não há um Go real para o BFF chamar. Esta tarefa portanto fecha essa lacuna, mas **de forma minimalista**: implementa em `cmd/server` só os três caminhos que `bff-api.yaml` (o contrato que o BFF de fato precisa satisfazer) realmente consome — `listRecords`, `createRecord` e um novo `getActor` (ver item 2) — não os cinco caminhos de `internal-api.yaml` inteiro. `getRecord`/`updateRecord`/`deleteRecord` por ID **não são implementados nesta tarefa**: `bff-api.yaml` não os expõe ao React (o "recorte representativo" de GO-006 optou por não cobrir edição por ID no BFF ainda), e `internal/records.UpdateRecord`/`DeleteRecord` exigem `expectedVersion`, que o contrato HTTP atual não tem como veicular em `DELETE` (sem corpo) — resolver isso é decisão de contrato para quando um consumidor real de edição existir (provavelmente GO-019, "Integrar editor ao BFF"), não fabricada aqui sem consumidor.
2. **Lacuna real descoberta: nenhum endpoint devolve o papel atual do ator.** ADR-0007 exige que "o BFF busca papel/permissões atuais no backend Go a cada requisição que precisar (via `ServiceIdentity`)" para o bootstrap — mas `internal-api.yaml` não tem nenhum endpoint de identidade/ator, só CRUD de registros. Adicionado `GET /v1/tenants/{tenant}/actor` (schema `Actor{id, role_id}`) a `internal-api.yaml` — extensão mínima e diretamente motivada pelo próprio ADR-0007, não escopo inventado. Implementado em `cmd/server` resolvendo o `sub` do token (ID do usuário) via um novo `identity.FindUserByID` (não existia; só havia `FindUserByEmail`/`FindUserByAPIToken`).
3. **`internal-api.yaml`'s `securitySchemes.ServiceIdentity` e `bff-api.yaml`'s `SessionCookie.name: connect.sid` divergem de ADR-0007 (que fixa o nome do cookie como `sc_session`).** ADR-0007 é a decisão específica e mais recente sobre exatamente este ponto ("GO-017 implementa exatamente este contrato"); `connect.sid` é o nome padrão do `express-session`, provavelmente um placeholder ilustrativo em GO-006, não uma decisão deliberada de sobrepor a ADR-0007. Corrigido em `bff-api.yaml` para `sc_session`, com uma nota citando a ADR.
4. **Sem consumidor de login real ainda:** nem `bff-api.yaml` nem `internal-api.yaml` definem um endpoint de autenticação (usuário+senha). O fluxo de login de UI é GO-018/GO-019 (frontend + editor). Esta tarefa implementa o MECANISMO de sessão (ADR-0007: cookie, store, troca por `ServiceIdentity`) como módulo testável — `session.ts` exporta `SessionStore`/`createSession`/middleware — sem expor uma rota pública de login (seria inventar uma superfície de API não contratada). Os testes de integração criam uma sessão diretamente no store (o equivalente de "um login já aconteceu"), o mesmo espírito de `metadata.Cache`/outbox handler "sem consumidor real ainda" já usado em tarefas anteriores.
5. **Store de sessão:** ADR-0007 exige "nunca o banco de domínio" mas deixa a tecnologia exata (Redis vs. Postgres de sessão separado) para esta tarefa. Sem infraestrutura Redis disponível neste ambiente de execução, implementado como uma interface `SessionStore` (get/create/touch/destroy) com uma implementação `InMemorySessionStore` — documentado explicitamente como decisão de estágio, a trocar por Redis/Postgres-de-sessão em produção real (mesmo padrão de `cutover.Guard` documentar sua natureza de cache em memória).
6. **CSRF e assinatura de `ServiceIdentity` implementados à mão vs. biblioteca:** `ServiceIdentity` (JWT HS256) usa a biblioteca `jsonwebtoken` (madura, evita reintroduzir bugs de verificação de assinatura/confusão de algoritmo que o próprio Go já tomou cuidado de evitar com `golang-jwt/jwt/v5`) — ao contrário do padrão "sem SDK externo" de ADR-0009, que se aplicava especificamente a observabilidade (sem coletor real para validar, formato aberto substituível depois); aqui a superfície é pequena, mas errar verificação de JWT é uma classe de bug com histórico conhecido, então usar uma biblioteca madura pesa mais que evitar a dependência. CSRF (padrão duplo-envio) é implementado à mão (mecanismo simples, comparação em tempo constante via `crypto.timingSafeEqual`, mesmo espírito de `identity.VerifyAPIToken`).
7. **Cliente HTTP tipado para o Go:** reaproveita os tipos gerados em `migracao/contracts/gen/ts` (`paths` do `internal-api.yaml`) da mesma forma que `gen/ts/client-example.ts` (GO-006) já demonstrou — `fetch` tipado por esses tipos, não um SDK gerado à parte. `AbortController`/timeout explícito em toda chamada (ADR-0003: "BFF precisa de timeout/circuit-breaker, não pode travar esperando indefinidamente").
8. **Teste de integração real de três camadas:** um teste automatizado de ponta a ponta com os três processos reais (Postgres + `cmd/server` real + BFF real) fica como verificação MANUAL documentada nesta execução (mesmo padrão do smoke test manual de `cmd/worker` em GO-014) — não commitado como script/CI permanente nesta entrega, para não ampliar ainda mais o escopo de infraestrutura de teste. A suíte automatizada cobre: lado Go (Postgres real, `httptest`, os três caminhos novos) e lado BFF (Node, mock do Go via `http.createServer` que replica a verificação de assinatura/tenant do `ServiceIdentity` para validar que identidade forjada/adulterada é rejeitada de ponta a ponta na fronteira que o BFF controla).

### Smoke test manual de três camadas (Postgres real + `cmd/server` real + BFF real)

Ambiente: container `saltcorn-go017-testdb` (`postgres:16-alpine`, porta local `55560`), binário real de `cmd/server` (`go build ./cmd/server`) e binário real do BFF (`npm run build`, executado via um pequeno script que seeda uma sessão diretamente no `InMemorySessionStore` — não há endpoint de login, ver nota de escopo #4). Tenant `smoketest`, usuário admin real (`identity.CreateUser`), tabela dinâmica real `widgets` (`metadata.CreateTable`/`AddField`), ownership de `tables.records` registrado para `go` (`cutover.SwitchOwner`).

1. `curl` direto ao Go real com um `ServiceIdentity` assinado manualmente: `GET .../actor` → `200 {"id":1,"role_id":1}`; `GET .../records` → `200 {"items":[],"next_cursor":null}`; `POST .../records` → `201` com o registro criado.
2. BFF real apontando para esse `cmd/server`, mesmo segredo compartilhado: `GET /api/bff/bootstrap` sem cookie → `401 session_required`; com sessão → `200 {"actor":{"id":1,"role_id":1},"tenant":"smoketest"}` (papel resolvido do Go real, não hardcoded); `GET .../records` → `200` com o registro criado no passo 1 (prova que o BFF lê do MESMO backend real); `POST .../records` sem `X-CSRF-Token` → `403 csrf_invalid`; com CSRF → `201`; **retry idêntico (mesmo corpo, mesma sessão)** → `201` com o MESMO `id`, confirmado por consulta direta ao Postgres (`SELECT id, label FROM smoketest.widgets` — exatamente 2 linhas, não 3).
3. `cmd/server` real derrubado (`kill`) com o BFF ainda de pé: `GET /api/bff/tables/widgets/records` → `502 domain_unavailable` (erro controlado, resposta imediata — não travou esperando).

Containers, binários e schema de teste removidos ao final (`docker rm -f saltcorn-go017-testdb`, processos finalizados).

### Decisões de escopo (preflight)

Precedidas por um levantamento dedicado (agente de pesquisa) da anatomia de plugin do legado, do que `base-plugin`/`sbadmin2` fornecem, do pack piloto `guitars` real, e dos ADRs 0005/0006 — resumo dos achados mais relevantes à decisão:

1. **"Definir contratos" é majoritariamente FORMALIZAR interfaces Go já existentes e esparsas, não inventar do zero** — achado do levantamento: `internal/types.Coerce`, `triggers.ActionFunc`, `views.View`+pipeline, e `internal/identity` já são, cada um, o ponto de extensão real para tipos/ações/views/auth; faltava documentá-los formalmente como um "SDK" coeso (ver README §"SDK de extensão") e, para ações e views, POPULAR o catálogo real, não só ter a interface pronta.
2. **A hipótese "o piloto `guitars` só depende de `run_js_code`, logo nenhum plugin de terceiro" é PARCIALMENTE REFUTADA** — achado concreto do levantamento: `pack.json` do `guitars_backup.zip` declara `@saltcorn/any-bootstrap-theme` (tema) e `@saltcorn/flatpickr-date` (fieldview de data), efetivamente exercitados pelas views `edit_guitar_process`/`edit_processed_embed`. Nenhum dos dois pacotes existe neste monorepo (confirmado por busca — zero pacotes `@saltcorn/*` de terceiro vendorizados). Decisão: substituição funcional no piloto (tema padrão `sbadmin2`, já base do frontend GO-018; campo de data nativo HTML5 em vez de `flatpickr`) — divergência visual/UX aceita e documentada, não um bloqueio às capacidades P0 do piloto.
3. **Ações nativas: só `send_email`/`webhook` são portadas nesta entrega, não o catálogo completo (~29 ações do legado).** Achado: a infraestrutura (`internal/notify`, GO-026) já existia pronta e testada, mas SEM NENHUM wiring em `Dispatcher.Actions` (zero ocorrências de `internal/notify` em `internal/triggers`, confirmado por grep) — essa é a lacuna real e concreta que esta tarefa fecha. `insert_any_row`/`modify_row`/`delete_rows` (CRUD dirigido por trigger) ficam de fora: precisam de desenho próprio (evitar loop de trigger sobre a própria escrita que originou o disparo, decidir o contexto de autorização do efeito) que não é incidental a "ligar e-mail/webhook já prontos". `run_js_code` fica PERMANENTEMENTE fora do catálogo nativo — por definição executa JS arbitrário, ADR-0005 mandata host sempre, nunca uma versão "portada".
4. **`Trigger.Configuration` (coluna `jsonb` nova) é uma extensão NECESSÁRIA, não incidental, ao mecanismo de GO-024.** Achado de implementação: antes desta tarefa, `Dispatcher.Actions` mapeava um NOME de ação para uma função ÚNICA e global — dois triggers com o mesmo nome de ação (ex.: dois `send_email` endereçados a destinatários diferentes) sempre executariam a MESMA função sem nenhum parâmetro próprio, o que torna ações genéricas reutilizáveis impossíveis de expressar. `ActionFunc` ganha um 5º parâmetro (`config map[string]any`, o `Trigger.Configuration` daquela instância) — mudança de assinatura propagada a todos os call sites existentes (dispatch.go, dispatch_test.go, 8 ocorrências), sem qualquer mudança de comportamento para triggers que já existiam (config vazio = comportamento idêntico ao anterior).
5. **Idempotência das ações nativas usa um hash do conteúdo de `Configuration` na chave, não só (ação, linha).** Achado de implementação, confirmado por regressão deliberada (ver abaixo): sem esse hash, dois triggers `send_email` DIFERENTES (destinatários diferentes) disparando sobre a MESMA linha colidem na MESMA chave de idempotência em `outbox.Do` — o Postgres rejeita a segunda inserção com `idempotency_key_conflict`, e a criação do registro INTEIRA falha (não é uma perda silenciosa de e-mail, é uma falha visível e confusa da operação de escrita). Corrigido incluindo um hash SHA-256 (truncado, 8 bytes) do JSON de `Configuration` na chave — dois triggers com config IDÊNTICA sobre a mesma linha continuam, razoavelmente, tratados como o MESMO evento.
6. **Interpolação de template é deliberadamente simples (`{{campo}}` → valor literal), não um motor de template completo.** Suficiente para os casos de uso de `send_email`/`webhook` desta entrega; um campo ausente vira string vazia, nunca erro — mesmo espírito tolerante de um template de notificação.
7. **`sbadmin2` confirmado como puramente apresentacional** (achado do levantamento: zero `types`/`actions`/`viewtemplates`/`authentication` exportados, única referência a `db` é leitura de uma string estática de versão) — usado para confirmar, não inventar, o contrato de "plugin de apresentação" que o critério de aceite exige (React/BFF nunca acessa persistência).
8. **`internal/identity` permanece deliberadamente NÃO extensível por plugin.** Login social/OAuth/SAML é bloqueador permanente, confirmado por busca direta no monorepo (zero pacotes `*auth*/*oauth*/*saml*` — não é falta de investigação, é ausência de código-fonte). `Password` (único método hardcoded do legado) já tem equivalente Go completo desde GO-008.
9. **Wiring de `Dispatcher`/`Evaluator`/`Workflow` em `cmd/server`/`cmd/worker` fica FORA desta entrega — mesma decisão de escopo já aplicada por GO-023/024/026.** Achado real: nenhum dos três está de fato conectado ao processo HTTP real hoje (grep confirma: `internal/triggers.Dispatcher` não aparece fora de `cmd/worker`'s import list nem em `cmd/server`; `createRecordHandler` chama `records.CreateRecord(..., nil)` — hooks sempre nil). Toda a cadeia de automação (GO-022→GO-025) está testada e correta, mas inerte em produção — item explícito na lista de "o que falta antes de desligar o legado" (ver README), não um problema desta tarefa especificamente, mas uma lacuna que ela documenta com precisão pela primeira vez.
10. **`Color` (6º tipo básico do legado) fica fora desta entrega** — sem uso pelo piloto `guitars` (só text/integer/boolean/float/date), e adicioná-lo tocaria `internal/metadata.FieldType`, `internal/records.validateValue` e `internal/pack` simultaneamente — risco desproporcional ao valor para esta entrega, dado o orçamento de esforço já consumido pelos itens 1-9.
11. **Verificação de regressão deliberada, três pontos**: (a) hash de `Configuration` removido da chave de idempotência — dois triggers `send_email` diferentes sobre a mesma linha colidem de verdade (`idempotency_key_conflict` real, não simulado); (b) validação de `config["to"]` vazio removida de `sendEmailAction` — e-mail sem destinatário seria enfileirado sem erro; (c) round-trip de `Trigger.Configuration` em `internal/pack` (não uma regressão de código quebrado, mas uma prova de que o campo novo realmente participa do export/import — o teste de round-trip byte-a-byte já existente cobre isso organicamente, sem precisar de uma quebra deliberada adicional).

### Achado de verificação (regressão deliberada, dois pontos)

1. **Hash de `Configuration` na chave de idempotência (`internal/triggers/actions.go`, `actionIdempotencyKey`)**: trocada por uma chave sem hash (`"trigger-action:%s:%v", action, row["id"]`). `TestSendEmailAction_TwoTriggersSameRowDifferentConfig_BothEnqueue` falhou com `CreateRecord: outbox: mesma chave de idempotência usada com payload diferente: "trigger-action:send_email:1"` — confirmando que, sem o hash, dois triggers `send_email` DIFERENTES sobre a mesma linha genuinamente colidem em `outbox.Do`, e a colisão propaga como falha da escrita inteira (409 de idempotência), não uma perda silenciosa isolada. Restaurado, suíte volta a passar.
2. **Validação de `config["to"]` obrigatório (`internal/triggers/actions.go`, `sendEmailAction`)**: removida a checagem `if len(to) == 0 { return ErrActionConfigInvalid }`. `TestSendEmailAction_MissingTo_ReturnsErrorWithoutEnqueuing` falhou com `err = <nil>, esperado ErrActionConfigInvalid` — confirmando que, sem a checagem, um `send_email` sem destinatário seguiria adiante silenciosamente (enfileiraria um e-mail com lista `To` vazia). Restaurado, suíte volta a passar.

- **Nota de escopo (investigação e decisão de design):**
  - **Investigação prévia (agente de exploração, sem escrita de código) confirmou o gap real:** `Compile` (GO-012) já checava `identity.CanRead(actorRole, table.MinRoleRead)` na tabela PRINCIPAL de uma `Query`, mas essa era a ÚNICA checagem do pacote inteiro. Nem o loop de `Joins` (que resolve `refTable` via `metadata.GetTableByID`) nem `compileAggregation` (que resolve `childTable` via `metadata.GetTable`) checavam o `MinRoleRead` da tabela referenciada/filha antes de expor suas colunas ou agregados. Não existe uma função de "count" dedicada — `Count` é só mais um `AggFunc` de `Aggregation`, então "contagem" herdava o mesmo gap de "agregações". Não existe função de "exportação" nem cache de resultado de consulta no pacote; `Rows` é o único ponto de execução pública, usado tanto para busca quanto para o que uma futura exportação usaria.
  - **Fix:** `Compile` agora chama `identity.CanRead(actorRole, refTable.MinRoleRead)` logo após resolver a tabela referenciada de um join, antes de listar colunas ou montar o `LEFT JOIN`. `compileAggregation` passou a receber `actorRole` e aplica a mesma checagem sobre `childTable` antes de montar a subquery escalar — cobre `Count`/`Sum`/`Avg`/`Min`/`Max` igualmente. Isso fecha exatamente o cenário do critério de aceite: um ator com acesso só à tabela pública não pode mais contornar a autorização trazendo colunas ou agregados de uma tabela admin-only via join/agregação.
  - **"Revogação imediata":** o papel do ator é um parâmetro explícito de toda chamada a `Compile`/`Rows` — nunca cacheado dentro de `internal/records`/`internal/identity`. Não existe hoje um mutador para `MinRoleRead`/`MinRoleWrite` de uma tabela já criada (só definidos em `metadata.CreateTable`), então a única "revogação" acionável no estado atual do código é a do papel do próprio ator entre duas chamadas — e essa já é trivialmente imediata por não haver cache algum. Um teste dedicado (`TestCompile_RevocationTakesEffectImmediately`) prova a ordem admin→público (nenhuma "carona" de uma leitura anterior bem-sucedida), complementando o teste já existente `TestCompile_AuthorizationDenied` (que prova público→admin).
  - **Caches:** `metadata.Cache` (GO-011) permanece sem nenhum consumidor de produção (confirmado por grep: nada em `internal/records` o referencia) — não há cache de resultado de consulta nem de decisão de autorização hoje para "aplicar política" a ele. Documentado no README em vez de fabricar uma integração sem consumidor real, mesmo espírito do próprio `metadata.Cache` desde GO-011.
  - **"Usar banco primário após escrita":** não existe réplica de leitura no backend hoje (`internal/platform/database.DB` abre um único `*pgxpool.Pool`, sempre usado por `WithTenant`/`WithTenantAndActor`) — confirmado por leitura de `database.go` e busca em ADRs. O requisito é hoje vacuamente satisfeito; documentado como tal, não fabricado.

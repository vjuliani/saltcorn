### Decisões de escopo (preflight)

1. **Escopo confinado a `internal/metadata` — não "todo o backend fala com SQLite".** GO-030 depende explicitamente de GO-011/012/013/014 (não de tarefas posteriores) — lido como sinal de que só o catálogo de tabelas/campos (GO-011) precisa de prova concreta de dual-backend nesta entrega, não `internal/records` nem `internal/platform/outbox`. Investigação confirmou por quê os outros dois são estruturalmente mais caros: `internal/records` usa `xmin` (coluna de sistema do Postgres, sem NENHUM equivalente SQLite) para todo o mecanismo de concorrência otimista (`_version`); `internal/platform/outbox` usa `pg_advisory_xact_lock` e `FOR UPDATE SKIP LOCKED`, sem equivalente direto no modelo de escritor único do SQLite. Portar qualquer um dos dois exigiria uma decisão de design de concorrência própria — não uma generalização mecânica como a de `internal/metadata` (que não usa `xmin` nem `FOR UPDATE SKIP LOCKED` em lugar nenhum, confirmado por leitura completa do pacote antes de decidir o escopo).
2. **`database.Tx` é uma fronteira NOVA e MÍNIMA, não uma reescrita de `WithTenant`.** Alternativas descartadas: (a) mudar `WithTenant`/`WithTenantAndActor` para devolver a nova interface diretamente — rejeitada, porque isso propagaria a mudança de tipo para TODO pacote do backend (records, outbox, triggers, scheduler, notify, files, library, config, pack, views, cutover, realtime, identity — todos tipados contra `pgx.Tx` concreto), um refactor de dezenas de arquivos fora do orçamento desta tarefa e do seu próprio escopo declarado; (b) manter `internal/metadata` só contra Postgres e criar uma reimplementação SQLite paralela — rejeitada por violar DRY (duas fontes de verdade para a mesma regra de negócio). Escolhida: `database.AsTx(tx pgx.Tx) Tx` adapta uma transação Postgres JÁ ABERTA (por `WithTenant`, sem NENHUMA mudança) no ponto de CHAMADA de `internal/metadata` — confinando o impacto a "envolver `tx` com `database.AsTx(tx)` nos ~24 arquivos que chamam funções de `internal/metadata`", nunca a uma mudança de assinatura de nenhuma outra função pública.
3. **`modernc.org/sqlite` (puro Go, sem cgo) em vez de `mattn/go-sqlite3` (cgo).** Confirmado por teste de compatibilidade de versão ANTES de adicionar a dependência: a versão mais recente (`v1.59.0`) exige Go ≥1.25; este módulo fixa a toolchain em `go 1.22` deliberadamente (README, "evitar exigir uma versão de Go mais nova que a documentada"). Pinado em `v1.36.0` — a mais recente release cujo `go.mod` ainda declara `go 1.21` (a seguinte, `v1.36.3`, já pula para `go 1.23.0`). Confirmado por smoke test isolado (fora do módulo, antes de qualquer código de produção) que `$1`/`$2` (placeholders posicionais do Postgres), `RETURNING`, e `INTEGER PRIMARY KEY AUTOINCREMENT` funcionam exatamente como esperado com este driver.
4. **"Modo desktop" = arquivo por tenant, sem pool — mesma decisão do legado (`packages/sqlite/sqlite.ts`), nunca um pool multi-tenant como o Postgres.** `internal/platform/sqlite.DB` nunca abre mais de UMA conexão física por arquivo (`SetMaxOpenConns(1)`) — decisão que também resolve "concorrência" (ver item 6) sem precisar de nenhum mecanismo de lock explícito.
5. **Só 2 divergências de sintaxe reais, confirmadas empiricamente, não a ampla divergência que a hipótese inicial temia.** `$N`, `RETURNING`, `ON CONFLICT ... DO NOTHING`, e a maioria dos nomes de tipo (`text`/`int`/`boolean`/`smallint`/`bigint` — SQLite não rejeita nomes de tipo desconhecidos, só os usa para inferir afinidade) funcionam sem NENHUMA mudança nos dois SGBDs. As duas divergências reais: (a) `id serial PRIMARY KEY` (Postgres) vs `id INTEGER PRIMARY KEY AUTOINCREMENT` (SQLite, literal exato exigido); (b) `ALTER TABLE ... DROP COLUMN IF EXISTS` — SQLite suporta `DROP COLUMN` desde 3.35, mas SEM `IF EXISTS`. A segunda foi um achado REAL durante a implementação (não uma regressão deliberada — o primeiro corpus de teste SQLite já pegou isso na primeira rodada, antes de qualquer verificação deliberada).
6. **`lockCatalog` diverge por DESIGN no SQLite, não por sintaxe.** `pg_advisory_xact_lock` (Postgres) vira um no-op deliberado no SQLite: como `SetMaxOpenConns(1)` já serializa estruturalmente qualquer mutação do MESMO tenant antes mesmo de `lockCatalog` rodar, um mecanismo de lock explícito seria redundante. Confirmado por regressão deliberada (10 `CreateTable` concorrentes sobre o MESMO arquivo, `_sc_metadata_version` termina em exatamente 10 com `SetMaxOpenConns(1)`; falha real com `SQLITE_BUSY` sem ele).
7. **`internal/pack`/`internal/pluginhost`/`internal/triggers`/`internal/views` etc. permanecem Postgres-only** — a mudança que os afeta é só "o argumento que passam para `internal/metadata` precisa ser `database.AsTx(tx)` em vez de `tx`", nunca uma mudança de comportamento ou de dependência de SQLite.
8. **Verificação de regressão deliberada, dois pontos** (mais um achado real não-deliberado, ver item 5b): (a) branch de `idColumnDDL` removido — `CreateTable` falha de verdade já na primeira linha de `_sc_tables` (`converting NULL to int is unsupported`); (b) `SetMaxOpenConns(1)` removido — 10 goroutines concorrentes falham de verdade com `SQLITE_BUSY` (não uma simulação).

### Achado de verificação (regressão deliberada, dois pontos, mais um achado real)

1. **`idColumnDDL` (`internal/metadata/schema.go`)**: removido o branch de dialeto, sempre retornando `"id serial PRIMARY KEY"`. `TestSQLite_CreateTable_CriaTabelaFisicaComAutoincremento` falhou já no PRIMEIRO passo (inserir em `_sc_tables`, que também usa `idColumnDDL`): `metadata: inserir tabela no catálogo: sql: Scan error on column index 0, name "id": converting NULL to int is unsupported` — confirmando que, sem o literal exato `INTEGER PRIMARY KEY AUTOINCREMENT`, o SQLite genuinamente não gera nenhum valor de id. Restaurado, suíte volta a passar.
2. **`SetMaxOpenConns(1)` (`internal/platform/sqlite/db.go`, `connFor`)**: removida a chamada. `TestWithTenant_ConcorrenciaMesmoTenant_SerializaSemPerderEscrita` (20 goroutines) falhou de forma consistente em 3 execuções seguidas com `database is locked (5) (SQLITE_BUSY)` — confirmando que, sem uma única conexão por arquivo, o SQLite genuinamente rejeita escritas concorrentes da mesma forma que rejeitaria em produção. Restaurado, suíte volta a passar.
3. **Achado real (não uma regressão deliberada) — `ALTER TABLE ... DROP COLUMN IF EXISTS` (`internal/metadata/catalog.go`, `DropField`)**: a primeira execução do corpus SQLite (antes de qualquer verificação deliberada) já falhou com `SQL logic error: near "EXISTS": syntax error` — SQLite suporta `DROP COLUMN` desde a versão 3.35, mas SEM a cláusula `IF EXISTS` (só Postgres tem essa variante). Corrigido com um branch de dialeto na construção da string de DDL (`dropColumnDDL`). Confirmado por regressão adicional (reintroduzindo `IF EXISTS` incondicional): a mesma falha reaparece de forma idêntica.

### Nota de escopo (decisões de design, fixadas antes da implementação)

1. **Base: o protótipo de GO-004, não uma reinvenção.** `docs/migracao-go/prototipos/GO-004-fronteira-rpc/` já validou o protocolo (JSON por linha, `kind: expr|call|db`, canal de `callback_request`/`callback_response` bidirecional, callback por NOME nunca por closure serializada) e mediu o custo (~2,6ms de piso por chamada, dominado pela instanciação da VM; overhead de callback de leitura ~0,2–0,6ms). GO-022 promove esse protocolo a produto, com as lacunas que o próprio relatório do GO-004 já apontava como pendentes: processo de vida longa (não subprocesso por chamada — recomendação #1 do relatório), isolamento real de SO/processo (não só a VM), limites de memória/tempo, protocolo de erros tipado, e capacidades explícitas (não "o host pode chamar qualquer callback registrado").
2. **`vm2` NÃO é usado no host final — decisão explícita do próprio ADR-0005/relatório GO-004.** O relatório de GO-004 usou `vm2` deliberadamente para medir a fronteira com o mecanismo real de produção, mas registra: "não é recomendação de continuar usando vm2 no host final". `vm2` está descontinuado com histórico de escape de sandbox. O host desta tarefa usa o módulo `vm` nativo do Node (`vm.Script`/`vm.createContext`, com `timeout` por execução) — não porque `vm` seja um sandbox mais forte (não é: ADR-0005 cita `vm.runInNewContext` como "sandbox mais fraco ainda" no contexto mobile), mas porque a ADR é explícita: **"simples uso de VM não constitui toda a fronteira de segurança"** — a fronteira de segurança real deste host é o PROCESSO isolado (memória limitada via `--max-old-space-size`, tempo limitado pelo lado Go com kill+respawn), não a VM. A VM é só a camada interna de conveniência (evita que uma expressão acidentalmente maligna tropece no host inteiro em vez de só na própria chamada), nunca a fronteira de confiança.
3. **Isolamento OS/processo real, testado por regressão deliberada — não uma alegação.** Três garantias, cada uma provada desabilitando o mecanismo e confirmando falha real, depois restaurando (mesma disciplina de toda a migração até aqui):
   - **Timeout:** uma chamada que excede o prazo (via `vm.Script({timeout})` OU um laço síncrono que nunca resolve) é interrompida; o processo do host, se ficar preso, é MORTO e um novo é gerado sob demanda — chamadas seguintes continuam funcionando.
   - **Crash:** se o processo do host morrer (OOM real via `--max-old-space-size`, ou morto externamente), a chamada em curso recebe um erro `crashed` tipado, e a PRÓXIMA chamada sobe um host novo automaticamente — nunca deixa o cliente Go travado esperando um processo morto.
   - **Acesso proibido:** uma chamada só pode invocar os callbacks que o lado Go explicitamente concedeu para aquela chamada (`capabilities: []string`) — tentar um callback fora da lista concedida falha com `capability_denied`, nunca executa.
4. **Callback de leitura genérico, reaproveitando autorização já existente — não um mecanismo de banco novo.** O canal de callback (recomendação #2 do relatório GO-004: "desenhar como mecanismo genérico, não um método por singleton") é resolvido do lado Go chamando `internal/records.Rows`/`internal/metadata`, com o MESMO `identity.CanRead`/papel do ator já usado em todo o resto do backend (GO-008/012/015) — nenhuma nova checagem de autorização inventada, e nenhuma credencial de banco cruza para o processo Node (ADR-0005: "sem credenciais irrestritas de banco").
5. **Escrita a partir de uma expressão/plugin fica FORA de escopo — não fabricada.** O relatório de GO-004 (§5) é explícito: callback de escrita não foi prototipado e não deve ser presumido seguro pelo mesmo mecanismo sem decisão própria de idempotência/rollback. GO-022 implementa e testa só o callback de LEITURA. Um plugin/expressão que precise escrever fica classificado como **bloqueador** (não suportado pelo host) até uma decisão dedicada — GO-023 ou posterior.
6. **"Plugin transacional incompatível mantém operação integral no legado" — reaproveita `internal/platform/cutover` (GO-009), não um mecanismo por-plugin novo.** Uma capacidade cujo plugin não se encaixa no host (depende de closure, precisa de escrita, ou usa singletons de domínio sem canal de callback — os três critérios concretos do relatório de GO-004 §3/§4) simplesmente NUNCA tem sua capacidade de ownership trocada para `OwnerGo`/host — o registro de `_sc_capability_ownership` (já existente, já testado por GO-009) continua em `OwnerLegacy` por padrão, e todo o tráfego dessa capacidade continua servido inteiramente pelo caminho legado. Isso é literal, não metafórico: reaproveita exatamente o mesmo "padrão seguro — nenhuma tenant+capacidade passa a ser servida por Go por omissão" (`cutover.OwnerOf`) já em produção desde GO-009.
7. **"Matriz de plugins atualizada" (critério de aceite) = refinar `inventario/GO-001-matriz-capacidades.md` §2.4 com o que o protótipo de GO-004 realmente provou, não um novo levantamento de plugins reais** (que continua não existindo neste checkout — lacuna já registrada desde GO-001/GO-003/GO-004). Antes de GO-004, a linha "Motor de expressões JS" estava classificada como **Bloqueador** simples; o protótipo provou que fórmulas puras e callbacks nomeados (incl. leitura) SÃO viáveis via host — a classificação é atualizada para refletir esse resultado real, com os três critérios concretos de incompatibilidade (closure, escrita, singleton sem callback) explícitos, não apenas "bloqueador" genérico.
8. **Sem wiring em `cmd/server`/validação de registros nesta tarefa.** Conectar o host a um caminho de validação real (ex.: `ownership_formula`, fórmulas calculadas em `CreateRecord`) é GO-023 ("Portar tipos e expressões prioritários"), que também decide QUAIS expressões são prioritárias — não fabricado aqui. GO-022 entrega a infraestrutura (host + cliente) validada por testes de integração próprios (Postgres real para o callback de leitura), não uma integração de produto ainda.

### Achado de verificação (regressão deliberada, três pontos)

1. **Timeout (domínio, `internal/pluginhost/client.go`)**: desabilitado o `killAndReset()` no branch `ctx.Done()` (`if false && ...`). `TestEval_Timeout_IsContained` não falhou com uma asserção simples — falhou com **`go test -race` reportando uma condição de corrida real**: sem matar o processo preso, a chamada SEGUINTE reaproveita o mesmo processo (ainda executando o laço infinito da chamada anterior), criando duas goroutines lendo o mesmo `bufio.Reader` concorrentemente. Restaurado, suíte volta a passar sem avisos de corrida.
2. **Crash (domínio, mesmo arquivo)**: desabilitado o `killAndReset()` no branch `errors.Is(o.err, ErrCrashed)`. `TestEval_Crash_IsContained` falhou com `"pluginhost: escrever no host: write |1: broken pipe"` — a chamada seguinte tentou usar um processo já morto. Restaurado, suíte volta a passar.
3. **`capabilities: null` → `runtime_error` em vez de `capability_denied` (achado durante a implementação, não uma regressão introduzida deliberadamente)**: `TestEval_CapabilityDenied_NotDeclared` falhou já na primeira execução (antes de qualquer regressão proposital) porque `Capabilities: nil` do Go vira `"capabilities": null` no JSON, e `null.includes` no host lançava um `TypeError` classificado como `runtime_error`. Corrigido com `req.capabilities ?? []` em `host.ts` — suíte passou a verde na sequência.

## Preflight — levantamento e decisões de escopo

Preflight delegado a um subagente de pesquisa (read-only) cobrindo as 15 ações nomeadas no escopo original desta task (`base-plugin/actions.ts` do legado) e o framework de ações nativas atual (`internal/triggers/{dispatch.go,actions.go}`). Achado central, verificado diretamente no código (não só no relatório do subagente): **a assinatura de `ActionFuncTx` (`ctx, tx, table, row, config`) não dava a NENHUMA ação um jeito de despachar outra ação/trigger recursivamente, nem de escrever pela via autorizada de `internal/records` (que exige `actorRole`)** — um problema que `RunJSCodeFuncTx` (GO-040) já havia resolvido para si mesma, sendo puxada para FORA do mapa `Actions` como um campo dedicado do `Dispatcher` com uma assinatura mais rica.

Dos 15 nomes do escopo original, o preflight (confirmado por leitura direta do legado, `packages/saltcorn-data/base-plugin/actions.ts`) encontrou:

1. **`toast`, `copy_to_clipboard`, `reload_embedded_view`, `progress_bar`, `duplicate_row_prefill_edit`** — NENHUM efeito do lado do servidor no legado. Cada `run()` devolve só uma diretiva para o NAVEGADOR consumir (`eval_js`, `goto`, `page_load_tag`/`progress_bar_update`) — `progress_bar` além disso lê `req.headers` diretamente, um parâmetro sem equivalente na assinatura de despacho. `ActionFuncTx` só devolve `error`; não tem como produzir nenhum desses resultados. Estender o contrato para isso seria uma mudança de framework maior que "adicionar 5 ações", fora do escopo desta task.
2. **`refresh_user_session`, `step_control_flow`** — sem conceito equivalente no Go. `refresh_user_session` renova uma sessão Express (`req.login`) — o backend Go é stateless/JWT, sem sessão de servidor a renovar. `step_control_flow` controla uma cadeia de "Multi-step action" (`halt_steps`/`goto_step`/`clear_return_values`, `models/trigger.ts:475-541`) — o modelo `triggers.Trigger` do Go tem um único `Action string`, sem nenhum conceito de trigger multi-etapa a controlar.
3. **`recalculate_stored_fields`** — depende de campos calculados/armazenados (`Field.calculated && Field.stored`), um conceito que não existe em NENHUM lugar de `internal/metadata` (`grep -rli "calculated"` não encontra nada). Não há o que recalcular.
4. **`download_file_to_browser`** — embute o arquivo inteiro em base64 no resultado da ação (`{download:{filename, mimetype, blob}}`). `ActionFuncTx` só devolve `error`; o mecanismo de GO-051 (`GET .../files/{id}`) é uma rota HTTP separada que streama a resposta, uma forma fundamentalmente diferente de "arquivo embutido no resultado de uma ação".
5. **`notify_user`** — bloqueada em `internal/notify.Create`, que GO-055 deixou DELIBERADAMENTE `pgx.Tx`-only (dependência transitiva de `internal/realtime.Publish`, também `pgx.Tx`-only, fora do escopo nomeado de GO-055). `ActionFuncTx` é `database.Tx`-based; não há como chamar `notify.Create` sem primeiro converter esse caminho — exatamente o que **GO-056** já existe para fazer. Anotado em GO-056 como extensão natural quando `notify.CreateTx` existir (ver `TASKS.md`/`tasks.csv`), não uma segunda tentativa aqui.

**Decisão de escopo**: das 15 ações nomeadas, **5 são portadas nesta task** (`sleep`, `duplicate_row`, `emit_event`, `set_user_language`, `loop_rows`) — as únicas com um efeito real do lado do servidor E um caminho viável dentro do framework atual (ou de uma extensão contida dele). As outras **10 ficam deliberadamente fora**, cada uma com evidência específica acima — nenhuma "fora de escopo por padrão" genérica.

### Extensão de framework: `ActionFuncTx` alargada

Para viabilizar `emit_event` (precisa despachar via `Dispatcher.EmitEventTx`), `loop_rows` (precisa despachar via `Dispatcher.RunOneTx` recursivamente) e `duplicate_row` (precisa escrever com `actorRole` via `records.CreateRecordTx`), a assinatura de `ActionFuncTx` foi alargada de `(ctx, tx, table, row, config)` para `(ctx, tx, d *Dispatcher, tenant, actorRole, table, row, config)` — mesmo precedente já usado por `RunJSCodeFuncTx` (GO-040) para o mesmíssimo problema, generalizado agora porque são VÁRIAS ações (não uma) que precisam do mesmo acesso. `sendEmailAction`/`webhookAction` (GO-029) foram atualizadas mecanicamente para a nova assinatura (parâmetros novos ignorados, nenhuma mudança de comportamento). Custo mecânico: ~13 literais de `ActionFuncTx` em 6 arquivos de teste (`internal/triggers/{dispatch_test.go,emitevent_test.go}`, `cmd/server/{events_test.go,sqlite_test.go}`, `internal/platform/sqlite/parity_test.go`) precisaram da mesma atualização de assinatura — sem mudança de comportamento, só a casca do tipo (mesmo padrão de custo mecânico já visto em GO-055 para os renomeios `Tx`).

## Achados reais (não hipotéticos)

1. **`duplicateRowAction` original falhava para QUALQUER linha**: a primeira versão só excluía `"id"` do mapa copiado, mas `records.RowsTx`/`CreateRecordTx` sempre incluem uma coluna sintética `"_version"` no mapa de linha (controle de concorrência otimista, `internal/records.VersionExpr`) — `records.validateFieldValues` rejeita explicitamente `_version` como campo definível diretamente (`ErrUnknownField`). Confirmado falhando genuinamente no PRIMEIRO teste real escrito (`TestDuplicateRowAction_CopiesRowWithoutIDAndFiresOwnTriggers`, erro `"_version" não pode ser definido diretamente`) antes da correção (excluir também `_version`).
2. **Recursão infinita real ao testar `duplicate_row` como trigger `AfterInsert` da própria tabela**: registrar `duplicate_row` como o PRÓPRIO trigger `WhenInsert` de "posts" faz a linha duplicada disparar o MESMO trigger de novo, ad infinitum — confirmado travando um processo `go test` real (matou uma transação Postgres aberta por >60s, sem crescimento de linhas commitadas, stack trace confirmou a recursão em `duplicateRowAction -> CreateRecordTx -> afterInsert -> RunOneTx -> duplicateRowAction`). Mesmo comportamento do legado (`table.insertRow` chamaria os MESMOS hooks) — não é uma divergência a corrigir, é um risco real documentado no comentário de `duplicateRowAction` e evitado no teste (chama a ação diretamente uma vez, nunca a registra como o próprio `AfterInsert` da tabela-alvo).

## Divergências deliberadas documentadas

1. **`sleep`**: só o ramo `sleep_where=="Server"` — o ramo padrão/cliente do legado devolve um `eval_js` executado no navegador, sem NENHUM efeito de servidor. Teto de segurança novo, `maxSleepSeconds=30`: como a ação roda DENTRO da mesma transação que disparou o trigger (`RunOneTx`), um `configuration.seconds` grande mantém uma conexão/transação Postgres aberta pelo tempo todo — um risco de esgotamento do pool que o legado não tem do mesmo jeito (lá a ação roda fora de qualquer transação SQL). Confirmado por regressão: sem o teto, um `seconds=3600` genuinamente trava a transação (ver Regressões).
2. **`duplicate_row`**: nenhuma tradução de fkey aninhado (o `row` do despacho de trigger já é sempre plano — `Query.Joins` nunca é usado pelo despacho).
3. **`emit_event`**: `configuration.payload` (expressão JS do legado que recalcula o payload) não é avaliado — sempre reemite a própria `row`. `internal/expression.Evaluator` só avalia para um `ExpectedType` escalar hoje, sem suporte a "resultado é um objeto arbitrário".
4. **`set_user_language`**: só a metade gravável (`identity.SetUserLanguageTx`) — o resto do legado (`req.login` para renovar o cookie de sessão Express, `res.cookie` para visitante anônimo) não tem equivalente: backend Go é stateless/JWT. `configuration.user_id` é EXPLÍCITO (nunca implícito a partir de "usuário da sessão atual") — o Dispatcher de triggers só propaga `actorRole` (um NÍVEL de papel), nunca uma identidade de usuário específica, mesma limitação já documentada para `RunJSCodeFuncTx`.
5. **`loop_rows`**: `configuration.where` é um MAPA JSON de igualdade pura (E lógico entre campos), nunca a expressão JS arbitrária do legado (`eval_expression`, que pode produzir qualquer operador via `mkWhere`) — cobre o caso de uso mais comum sem reintroduzir um segundo avaliador de expressão dentro do catálogo de ações. `configuration.interval` (pausa entre iterações) NÃO suportado — o mesmo risco de segurar uma transação documentado em `sleep` se multiplicaria por N linhas do laço, um risco estritamente pior.
6. **10 ações excluídas** — ver Preflight acima para a evidência específica de cada uma.

Nenhuma nova task de follow-up foi aberta para as 9 exclusões arquiteturalmente permanentes (sem conceito equivalente/sem efeito de servidor); a exclusão de `notify_user` foi anotada como extensão natural de GO-056 (já TODO, já cobre a dependência bloqueadora).

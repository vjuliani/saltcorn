- **Nota de escopo (decisão de design):**
  - DSL de filtros portado (`packages/db-common/internal.ts`, `mkWhere`/`whereClause`): igualdade implícita, `IN`/`NOT IN`, `ILIKE` (substring), `>`/`>=`/`<`/`<=`, intervalo (`Between`), `IS NULL`, `AND`/`OR`/`NOT`. Todo valor é parametrizado (`$1, $2...`), nunca interpolado.
  - Deliberadamente fora de escopo (documentado, não fabricado): busca full-text (`_fts`, exige configuração de idioma/tsvector), consultas de JSON path (GO-011 não tem tipo de campo JSON), sub-selects (`inSelect`/`inSelectWithLevels`), slugify, operador de regex, geo — nenhum destes tem o tipo de campo ou a infraestrutura correspondente em GO-011 ainda.
  - "Joins" = um nível de `LEFT JOIN` através de um campo `key` (GO-011) para trazer colunas da tabela referenciada — não multi-hop através de caminhos de relação.
  - "Agregações" = subquery escalar por linha (`COUNT`/`SUM`/`AVG`/`MIN`/`MAX`) sobre uma tabela filha que referencia a tabela consultada via campo `key` — o padrão de "agregação" do Saltcorn legado (contagem de registros relacionados, etc.).
  - "Chaves compostas" do critério de aceite: GO-011 só criou tabelas com PK simples (`id serial`) — não existe PK composta no catálogo. Interpretado como "condições de filtro compostas por múltiplos campos" (múltiplas entradas do mapa `Where`, combinadas com E implícito, replicando a semântica exata de `Object.entries(whereObj).map(whereClause).join(' and ')` do legado) — decisão registrada aqui, não uma lacuna escondida.
  - "Corpus compara resultados... com legado": sem um processo Node legado rodando neste ambiente de execução para comparação lado a lado ao vivo, o corpus é construído em Go usando o MESMO shape de fixture referenciado em GO-001/GO-002 (`books`/`patients`, campos `author`/`pages`/`favbook` tipo `key`) e testado quanto ao comportamento SQL correto (contra Postgres real), não uma comparação byte-a-byte de saída HTTP entre runtimes.
  - Identificadores nunca vêm de string livre interpolada: todo nome de campo/tabela passa por `metadata.GetTable`/`ListFields` antes de virar SQL — uma consulta que referencia um campo/tabela inexistente é REJEITADA (`ErrUnknownField`/`ErrUnknownTable`), não sanitizada-e-aceita — mais estrito que o legado (que só sanitiza o nome, sem validar contra um catálogo).

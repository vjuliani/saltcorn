## Preflight — levantamento e decisões de escopo

Preflight cobriu o legado (`routes/notifications.ts`, `manifest.mjs`/`pwa.ts` do client legado), o mecanismo de evento nomeado já portado (`internal/triggers.Dispatcher.EmitEvent`, GO-052), e a arquitetura de resolução de tenant do BFF (`migracao/packages/bff/src/{app.ts,selfhost.ts}`). Achados centrais:

1. **O legado usa um truque de spread de objeto para o mapeamento payload→row.** `Trigger.emitEvent("ReceiveMobileShareData", null, user, {row: body})` chama internamente `action.run({..., row: payload, ...(payload||{})})` — como o spread de `payload` vem DEPOIS de `row: payload` no mesmo literal, e `payload` (`{row: body}`) já tem uma chave `row`, essa chave SOBRESCREVE a atribuição inicial, fazendo o `row` final da ação ser `body` diretamente (não `{row: body}` aninhado). Isso é uma peculiaridade específica do legado sem equivalente necessário em Go: `Dispatcher.EmitEvent`/`EmitEventTx` já passa `payload` DIRETO como `row`, então o handler Go precisa passar `body` diretamente como payload — nunca envolvido em `{row: body}}` — para preservar o mesmo formato de linha que as ações já testadas em GO-052 esperam.
2. **O BFF não tem NENHUM mecanismo de resolução de tenant anônima fora do modo self-hosted.** `requireSession` resolve tenant inteiramente da sessão (`data.tenant`) no modo geral/hospedado — não existe resolução por subdomínio/Host header em lugar nenhum do código. A única exceção é `selfHostedListener`, cujo `options.tenant` é um valor FIXO conhecido no início do processo (de `internal/installation.Config.Tenant`), adequado para uma instalação desktop single-tenant. Isso é uma restrição arquitetural genuína, não uma lacuna de implementação.
3. **O harness de E2E (`migracao/e2e/scripts/start-bff.mjs`) usa `buildRouter` diretamente, nunca `selfHostedListener`** — rotas registradas somente em `selfHostedListener` (como `/manifest.json`) são genuinamente inalcançáveis a partir da suíte E2E padrão. Descoberto por leitura de código ANTES de escrever o spec E2E original (que incluía um teste de `GET /manifest.json` que teria falhado por um motivo de infraestrutura de teste, não um bug real).

**Decisões de escopo tomadas no preflight (divergência deliberada, mesma disciplina de "aceitar fora de escopo" de GO-050):**

- **`GET /manifest.json` servido SOMENTE no modo self-hosted do BFF.** Não existe resolução de tenant anônima no modo hospedado geral — expor o manifesto ali exigiria inventar um mecanismo novo (subdomínio/Host header) fora do escopo desta task e sem precedente na base de código.
- **`share_target.enctype` = `application/x-www-form-urlencoded`** (somente texto: `title`/`text`/`url`) em vez de `multipart/form-data`. Compartilhamento de ARQUIVOS via este caminho HTTP específico fica fora de escopo — o mecanismo de trigger subjacente para payloads com arquivo já foi provado em GO-052 por outro caminho de invocação; só a extensão do Web Share Target para aceitar arquivos multipart é adiada.
- **`install_progressive_web_app` (ação client-side) inteiramente fora de escopo, decisão permanente — nenhuma task de follow-up aberta.** Não existe mecanismo de ação client-side (`eval_js` ou equivalente) em nenhuma camada de Go/BFF/frontend, e navegadores modernos já oferecem prompt de instalação PWA automaticamente assim que um manifesto válido existe (que é exatamente o entregável desta task). Reintroduzir esse mecanismo só para uma única ação de conveniência não se justifica.

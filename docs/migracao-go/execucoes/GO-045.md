### Decisões de escopo (preflight e execução)

1. **Achado real de leitura do legado: `Table.deleteRows` NUNCA chama `insert_history_row`.** O texto original desta task presumia "grava histórico a cada update/delete" — busquei "insert_history_row"/"versioned" dentro do corpo INTEIRO de `deleteRows` (packages/saltcorn-data/models/table.ts, ~200 linhas) e não há NENHUMA chamada. Só `updateRow`/`insertRow` gravam histórico. Uma linha deletada simplesmente some da tabela principal; seu último snapshot de histórico continua sendo o do último insert/update — consultar `get_history` de um registro já deletado continua funcionando (a tabela `__history` não tem FK ON DELETE CASCADE para a tabela principal). Decisão: seguir o comportamento REAL, não o texto do aceite — `DeleteRecordTx` nunca chama `insertHistoryRow`, com um teste de regressão dedicado (`TestDeleteRecordTx_VersionedTable_DoesNotAddHistoryEntry`) para que uma futura "correção" que pareça mais completa não reintroduza a divergência.
2. **Nomenclatura deliberadamente distinta: `_history_version`, não `_version`.** `internal/records` (GO-013) já usa `_version` para controle de concorrência otimista (xmin no Postgres) em TODA tabela dinâmica — usar o mesmo nome para "posição na linha do tempo do histórico" (o `_version` do legado em `__history`) colidiria conceitualmente e, pior, colidiria de NOME real se algum código genérico tentasse ler `record["_version"]` esperando xmin. A tabela de histórico usa `_history_version`/`_history_time`/`_restore_of_version` — nomes que nunca aparecem na tabela principal.
3. **Carve-out documentado: tags cobrem só Table/View, nunca Page nem Trigger.** Page: páginas nunca foram portadas para Go (achado repetido desde GO-001) — não há o que uma TagEntry de página referenciaria. Trigger: ao tentar espelhar `tag_pack()` do legado (que usa `trigger.name` para tornar a referência portável, mesma convenção de "todo Pack é por nome, nunca por ID interno" já documentada em `internal/pack/types.go`), descobri que `internal/triggers.Trigger` (GO-024) NUNCA modelou um campo `Name` — só `TableID+When+Action+OnlyIf+AfterCommit+Configuration`. Sem nome, uma TagEntry de trigger não seria portável entre tenants/instalações, quebrando a única invariante que dá sentido ao formato de Pack. Candidata a task futura se/quando triggers ganharem nome — não um esquecimento.
4. **Deliberadamente fora de escopo: exposição HTTP/CLI/UI de tags.** Confirmei (`grep -rn "pack.Export\|pack.Import" cmd/`) que `internal/pack.Export`/`Import` em si NUNCA foram expostos via HTTP/CLI em nenhuma task anterior (GO-027 só entregou o pacote de domínio) — expor tags via API seria uma extensão maior que o próprio Export/Import completo ainda não tem. Tags ficam só no domínio Go, exaustivamente testado (CRUD, idempotência, integração com Export/Import/filtro), mesmo estágio de maturidade que o resto de `internal/pack`.
5. **Deliberadamente fora de escopo: undo/redo explícito.** O legado tem `undo_row_changes`/`redo_row_changes` (navegação por cadeia de `_restore_of_version`, útil para um botão "desfazer" de UI). O aceite desta task fala em "consultar/restaurar uma versão anterior" — satisfeito por `GetHistoryTx`/`RestoreRowVersionTx` sozinhos; a navegação de conveniência fica de fora (nenhuma UI React consumiria isso nesta entrega de qualquer forma).
6. **`restoreRecordVersionHandler` não dispara `Dispatcher.HooksFor` (triggers).** Mesmo padrão que `updateRecordHandler` tinha ANTES de GO-040 corrigir — mas aqui deliberadamente NÃO estendido: threading o dispatcher para este handler novo é uma extensão pequena e segura de se fazer depois (sem mudança de contrato), fora do orçamento desta task já grande. Documentado, não escondido.

### Achados reais encontrados durante a execução (não previstos no preflight)

**1. `fieldMap` injeta uma entrada sintética `"id"` — duplicava a coluna `id` em `insertHistoryRow`/`GetHistoryTx`/`RestoreRowVersionTx`.** `internal/records/compiler.go:fieldMap` sempre inclui `m["id"] = idField` (para que joins/consultas tratem "id" como um campo qualquer) — meus três loops que iteram `fieldsByName` para montar a lista de colunas incluíam "id" de novo, já que eu também já tinha "id" hardcoded para a PK da tabela de histórico. Postgres rejeitou com `column "id" specified more than once`, pego pelos testes desta task (`TestCreateAndUpdate_VersionedTable_GrowsHistory` e outros, na primeira rodada). Corrigido pulando `name == "id"` explicitamente nos três lugares.

**2. `UNIQUE (tag_id, table_id, view_id)` nunca detecta conflito quando uma coluna é NULL — `AddEntry` não era idempotente na prática.** Regra SQL padrão: NULL não é igual a NULL em checagem de unicidade. Como `TagEntryRef.validate()` garante que SEMPRE exatamente uma de `TableID`/`ViewID` é nil, a constraint composta nunca via duas linhas como conflitantes — `AddEntry` chamado duas vezes com a MESMA referência inseria uma SEGUNDA linha idêntica. Pego por `TestAddEntry_TableAndView_IdempotentAndListable` (esperava 2 entries, achou 3). Corrigido com dois ÍNDICES ÚNICOS PARCIAIS (`WHERE table_id IS NOT NULL` / `WHERE view_id IS NOT NULL`) em vez de uma UNIQUE composta — cada índice só enxerga as linhas onde sua coluna é preenchida, nunca esbarra em NULL.

**3. Nome de teste longo demais truncava dois schemas de tenant para o MESMO prefixo de 63 bytes.** `TestExportFilteredByTag_IncludesOnlyTaggedEntitiesPlusTransitiveClosure` (nome original) combinado com os sufixos `_filtered`/`_filtered_dest` de dois tenants distintos truncava, em `tenancy.SchemaName`, para o MESMO prefixo — os dois tenants viravam o MESMO schema físico, e o segundo `Import` (num tenant "novo") colidia com a view já criada pelo primeiro Export. Risco já documentado no comentário de `newTenant` (fixture_test.go) — corrigido renomeando o teste para `TestExportByTag_Filtered` (mais curto), não um bug de produto.

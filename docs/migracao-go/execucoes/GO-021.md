### Nota de escopo (decisões de design, fixadas antes/durante a implementação)

1. **Achado corretivo importante: HÁ ferramenta de navegador automatizável neste ambiente.** GO-018/019/020 documentaram repetidamente "sem ferramenta de browser/screenshot disponível neste ambiente" — essa afirmação está **desatualizada/imprecisa**: Playwright (`1.63.0`) está instalado (`deploy/playwright`, usado por GO-002) e um Chromium headless real (`~/.cache/ms-playwright`) já está em cache e FUNCIONA (`browser.launch()` + navegação real testados nesta tarefa). O que nunca esteve disponível é um navegador INTERATIVO para eu (o agente) "ver" uma tela durante a conversa — mas isso é diferente de "não dá para escrever um teste E2E automatizado que dirige um navegador real". GO-021 corrige essa lacuna: entrega Playwright E2E de verdade contra o novo stack (Go + BFF + React), não mais um teste HTTP travestido de "E2E mais realista possível".
2. **Navegadores cobertos: Chromium e Firefox, confirmados funcionais; WebKit excluído por limitação real do ambiente.** `npx playwright install firefox` baixou e `firefox.launch()` funcionou. `npx playwright install webkit` baixou, mas `webkit.launch()` falha (`Host system is missing dependencies... libavif16`) e este ambiente não tem acesso root (`sudo` exige senha) para instalar a dependência de sistema faltante. Documentado como limitação verificada, não evitada por conveniência — mesmo o suite Playwright LEGADO (`deploy/playwright/playwright.config.js`) só habilita `chromium` (Firefox/WebKit comentados), então nem sequer havia precedente de WebKit funcionando neste repositório antes desta tarefa.
3. **Sem endpoint de login real (gap já documentado em GO-017/019) — sessão do harness semeada diretamente, não uma fabricação de login.** O BFF não expõe (por decisão explícita, documentada desde GO-017) nenhum endpoint de autenticação usuário+senha — `InMemorySessionStore` é criado vazio e só ganha sessões via chamada direta a `.create(...)` nos próprios testes do BFF (`withSession`, `editor.test.ts`). Para o navegador real do harness "estar logado", `migracao/e2e/scripts/start-bff.mjs` (novo) importa os MESMOS módulos de produção do BFF (`buildRouter`, `createRequestListener`, `InMemorySessionStore`, `sessionCookieHeader`/`csrfCookieHeader`) e faz a MESMA chamada de semeadura que os testes do BFF já fazem — só que grava o `sc_session`/`sc_csrf` resultante num arquivo que o Playwright injeta no navegador via `context.addCookies`, em vez de usar em chamadas `fetch` de teste. Nenhuma rota nova é adicionada ao BFF de produção (`migracao/packages/bff/src/`) — a semeadura vive inteiramente em `migracao/e2e/`, fora do runtime real.
4. **Cookies injetados com `secure: false` — simplificação documentada do harness, não uma alegação sobre produção.** `sessionCookieHeader`/`csrfCookieHeader` (ADR-0007) sempre incluem `Secure`, que exigiria HTTPS local (certificado autoassinado) para o navegador aceitar o cookie via `Set-Cookie` de verdade. Como o harness usa `context.addCookies` (injeção direta no cookie jar do Playwright, não um `Set-Cookie` de resposta), a URL é `http://localhost` e o atributo `Secure` é setado como `false` só na injeção — o comportamento de `Secure` em si já tem teste unitário dedicado (`sessionCookieHeader inclui os atributos fixados em ADR-0007`, BFF) e não precisa ser reprovado aqui; o objetivo deste harness é a experiência de UI/UX, não a política de cookies.
5. **`cli e2e-seed` (novo comando Go) — não existia nenhum jeito de inicializar um tenant/admin/ownership sem passar por dentro dos próprios testes Go.** Criar o primeiro usuário e conceder ownership de capacidade são, por natureza, ações anteriores a qualquer requisição HTTP autenticada — não existe (nem deveria existir) uma rota pública para isso. `cmd/cli` já documentava desde GO-005 que "tenant/user CRUD... entra conforme os domínios forem portados" (paridade com `saltcorn create-user`/`reset-schema` do CLI legado, matriz GO-001 §2.6) — `e2e-seed` é essa entrada mínima, focada no que o harness de E2E precisa (recria o schema do zero, cria um admin, registra ownership de Go para `tables.records`/`tables.schema`/`tables.views`), não um comando de administração completo.
6. **Achado real de bug, encontrado só ao rodar um navegador de VERDADE: CORS entre o frontend e o BFF em portas diferentes.** Nenhuma suíte anterior (jsdom/vitest não faz requisição de rede real; HTTP direto sem navegador não aplica política de CORS) exercitava isso. `EditorPage.tsx` criando uma tabela via `fetch()` real, num navegador real, contra o BFF numa porta diferente da do frontend, falhava com "blocked by CORS policy" — a topologia de produção documentada (`VITE_BFF_BASE_URL` vazio, mesma origem via proxy reverso) nunca precisou de CORS, então o problema nunca apareceu até este harness. Corrigido em `migracao/packages/frontend/vite.config.ts` (`server.proxy`/`preview.proxy` para `/api/bff`) — sem tocar em nenhum código de produção do BFF.
7. **Achado real de bug operacional no PRÓPRIO harness: `(cd DIR && cmd) &` não referencia o processo real com `$!`.** A primeira versão de `run.sh` matava só o PID capturado de cada `&`, mas o frontend era iniciado como `(cd "$FRONTEND_DIR" && ... npx vite preview ...) &` — uma SUBSHELL, cujo PID não é o do processo `vite preview` de verdade (`npx` ainda spawna um processo filho). O `vite preview` ficava órfão, ainda escutando a porta depois do script terminar; a execução SEGUINTE via `wait_for_port` via a porta "aberta" e seguia em frente, mas na verdade estava conversando com o bundle/BFF de uma execução ANTERIOR já morta (sessão/tenant que não existem mais) — um falso "tudo pronto" que produzia falhas silenciosas e difíceis de diagnosticar (createTable nunca chegava ao Go, sem nenhum erro claro). Corrigido: `run.sh` libera as portas usadas ANTES de começar (`fuser -k`) e o cleanup mata o GRUPO DE PROCESSOS inteiro (`kill $(jobs -p)`), não PIDs individuais rastreados um a um.
8. **Achado real de bug pré-existente (desde GO-017): `new URL(path)` sem base lança "Invalid URL" quando `baseUrl` é vazio.** `bffClient.ts`'s `listRecords` (GO-017), `listViews`/`renderView` (GO-020) constroem uma `URL` para manipular query params via `new URL(`${baseUrl}${path}`)` — SEM um segundo argumento de base. Com `baseUrl` vazio (a topologia real de produção documentada — mesma origem via proxy reverso), o resultado é um path relativo (`"/api/bff/views"`), e `new URL()` de um path relativo SEM base lança `TypeError: Invalid URL` imediatamente. Nenhum teste anterior pegava isso porque `bffClient.test.ts` sempre usava uma `baseUrl` absoluta de teste (`"http://bff.local"`) — só um navegador real, com a configuração real (`VITE_BFF_BASE_URL` vazio), exercitava esse caminho. Corrigido com um helper `buildUrl(path)` que usa `window.location.origin` como base (ignorado quando `baseUrl` já é absoluto) — regressão confirmada deliberadamente (reintroduzir `new URL(path)` sem base, ver os 3 novos testes em `bffClient.test.ts` falharem com "Invalid URL", restaurar).
9. **Achado de integração corrigido: `EditorPage.tsx` criava views com um layout incompatível com o runtime de renderização (GO-020).** O layout de mock de GO-018/019 (`{above: [...]}`) nunca tinha sido exercitado contra a checagem de compatibilidade que GO-020 introduziu depois — "Publicar" falharia de verdade (422 `view_unsupported`) contra o backend real, algo que só um teste que efetivamente completa o fluxo "criar/publicar/operar" de ponta a ponta (não mocks) revelaria. Corrigido: `handleCreateTable` agora também cria um campo (`titulo`, texto) e a view nasce com um layout suportado (`layout.besides` referenciando esse campo); `handleSave`/`handlePublish` também passaram a distinguir `ViewUnsupportedError` de outros erros, mesmo padrão de `ViewConflictError`.
10. **Escopo real coberto vs. escopo do enunciado da tarefa ("React + SB Admin 2, i18n, responsividade, teclado, temas das aplicações, assets, sanitização HTML e componentes customizados do piloto") — nem toda palavra do enunciado tem hoje uma funcionalidade correspondente no stack novo para validar:**
    - **Cobertos de verdade nesta tarefa:** fluxo criar tabela → criar view → publicar → operar (visualizar) via SB Admin 2 real, ponta a ponta em navegador real; navegação/teclado básicos na Sidebar/Shell (GO-018); responsividade (viewport móvel e desktop); sanitização HTML (injeção de conteúdo malicioso num valor de registro, confirmando que o React nunca o executa).
    - **Sem funcionalidade correspondente ainda — fora de escopo, não fabricado:** **i18n** (nenhum framework de internacionalização existe no frontend novo — só texto em português fixo); **temas das aplicações** (nenhum sistema de tema por aplicação existe — só o CSS fixo do SB Admin 2, GO-018); **componentes customizados do piloto** (nenhum sistema de fieldview/plugin foi portado — GO-020 só suporta colunas de campo direto como texto puro, matriz GO-001 §2.3/§2.5 documenta que plugins de terceiro ficam no "bridge Node" ainda não implementado, GO-022). Registrar aqui em vez de simular uma cobertura que não existiria de verdade.
11. **"Nenhum script não autorizado executa em cenários de teste"** é testado literalmente: um registro com um valor contendo `<script>` é criado via API real, exibido via `ListView` (GO-020), e o teste verifica tanto que o React renderiza o texto ESCAPADO no DOM (nunca como HTML/script interpretado) quanto que nenhum efeito colateral de execução ocorreu (um marcador global `window.__xssMarker` nunca é setado) — prova ativa, não só ausência de erro.

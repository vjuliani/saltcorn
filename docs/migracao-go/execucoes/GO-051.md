## Preflight — levantamento e decisões de escopo

Carve-out já registrado no texto de GO-039 (ver `docs/migracao-go/execucoes/GO-039.md`) — as três lacunas que aquela task deixou explicitamente para esta: view aninhada, viewtemplate Feed, campo de arquivo. Extração real de `deploy/playwright_mobile/backups/guitars_backup.zip` (mesma metodologia de GO-039, `pack.json` como fonte de verdade) confirmou:

1. `create_guitar` embute `edit_processed_embed` via um nó de layout `{"type": "view", "view": "edit_processed_embed", "relation": ".guitars.processed$guitar"}` — `configuration.layout`, nunca `configuration.columns[]` (que só lista `description`/`name`/`Save`). Única sintaxe de `relation` encontrada no pack: `.{tabelaPai}.{tabelaFilha}${campoFK}`.
2. `guitar_feed` usa o viewtemplate `Feed`, cuja `configuration` é `{"show_view": "show_guitar", "view_to_create": "create_guitar"}` — nenhuma coluna própria, todo o trabalho de leitura/apresentação é delegado à view Show referenciada.
3. `upload_photo` usa a fieldview `"upload"` sobre um campo cujo tipo (`FieldFile`) não existia em `internal/metadata`.

**Decisões de escopo tomadas no preflight:**

- **Exceção deliberada à regra "layout nunca é fonte de dados" (GO-039)**: `configuration.layout` é lido, mas SÓ para localizar nós `type: "view"` — nenhuma outra leitura de layout foi introduzida. Documentado no cabeçalho de `internal/views/edit.go`.
- **`maxNestedViewDepth = 1`**: uma view aninhada não pode, por sua vez, embutir outra — erro explícito (`UnsupportedLayoutError`), nunca recursão silenciosa. Nenhuma view do pack piloto aninha mais de um nível, então este limite não corta nenhum uso real conhecido.
- **Sem UI para "adicionar uma linha filha nova"**: o backend só conhece o formato de campos de uma view filha a partir de linhas JÁ EXISTENTES (`NestedEditPlan.Rows`); com zero linhas não há formato para montar um formulário em branco. Editar/salvar linhas EXISTENTES já satisfaz o critério de aceite literal ("renderiza e salva... embutido").
- **`FieldFile` reaproveita a representação física de `FieldKey`** (inteiro, `coerceJSONValue`/`validateValue`), mas aponta para a tabela FIXA `_sc_files` (GO-026), nunca uma tabela dinâmica do tenant — evita estender `FieldDef.References`.
- **`internal/files` (GO-026) deliberadamente não tinha consumidor HTTP** ("um consumidor HTTP real fica para uma tarefa futura dedicada", comentário do próprio pacote) — esta task constrói esse consumidor (`cmd/server/files.go`) do zero.
- **Fluxo upload-depois-referencia, não multipart do formulário inteiro**: o campo de arquivo é enviado primeiro (`POST .../files`, devolve um id), a submissão do Edit é uma chamada JSON separada com esse id como valor do campo — evita precisar de parsing multipart dentro de `SubmitEditView`.

### Regressões deliberadas (uma por camada)

1. **Go (`internal/views.resolveNestedEditPlans`)**: desativar a checagem `if relParent != parentTableName` (trocada por `if false && ...`) → `TestCompileEditPlan_NestedView_RelationMismatch_IsUnsupportedLayoutError` falha de verdade: `CompileEditPlan com relation incompatível erro = <nil>, esperado *UnsupportedLayoutError` → restaurado → volta a passar (`TestCompileEditPlan_NestedView_*`: 3/3 PASS).
2. **BFF (`src/multipart.ts`)**: trocar o delimitador de `--${boundary}` para `${boundary}` (remove o prefixo `--` obrigatório do formato multipart, desalinhando onde cada parte começa) → o teste de ciclo completo falha comparando bytes DIFERENTES dos enviados (`'conteúdo real do teste\r\n\r\n'` recebido em vez de `'conteúdo real do teste'`) — não um erro de parsing, um dado silenciosamente CORROMPIDO, a pior classe de falha para um parser binário → restaurado → 39/39 volta a passar.
3. **Frontend (`EditView.tsx`)**: mover o grupo de views aninhadas para DENTRO do `<form>` pai (reintroduzindo o bug de HTML que já tinha sido corrigido antes de rodar qualquer teste, ver Achados) → o teste dedicado `"nunca desenha <form> aninhado"` falha de verdade: `container.querySelectorAll("form")` encontra um `<form>` dentro de outro → restaurado → 14/14 volta a passar.

### Achados reais corrigidos durante a execução (não são bugs de produto do motor em si)

1. **Bootstrap/ownership, mesma classe recorrente de GO-040/045/047/048**: `cmd/cli/e2eseed.go` e as fixtures HTTP de `cmd/server` (`records_test.go`, `views_test.go`) não chamavam `files.EnsureSchema`, e `e2eseed.go` não registrava a capability `"files"` na lista de ownership passada a `cutover.SetOwner`. Corrigido proativamente por inspeção, ANTES de qualquer teste revelar a lacuna via falha — aplicando a lição já documentada nas quatro tasks anteriores.
2. **Harness de E2E**: `migracao/e2e/run.sh` não definia `SALTCORN_GO_FILES_ROOT_DIR` ao lançar o backend Go. Confirmado por evidência de falha GENUÍNA antes da correção: o log do backend mostrava `WARN ... SALTCORN_GO_FILES_ROOT_DIR não configurada — upload/download de arquivo indisponível (503 files_unavailable)`, e a primeira execução do novo spec `nested-feed-upload.spec.ts` falhava de verdade no teste de upload (`POST .../files` devolvendo 503, o registro criado guardando um objeto de erro em vez de um id numérico no campo `photo`: `expect(typeof fileId).toEqual("number")` recebendo `"object"`). Corrigido acrescentando `FILES_ROOT_DIR=$(mktemp -d)` ao bloco de variáveis (com limpeza em `cleanup()`); rerodado o mesmo spec — 4/4 (Chromium+Firefox) passou.
3. **Bug real de HTML, encontrado e corrigido ANTES de rodar qualquer teste** (por raciocínio direto sobre a composição de `<EditView>`, não por uma falha de teste): a primeira versão compunha `<EditView>` recursivamente para as linhas filhas DENTRO do `<form onSubmit={...}>` da view pai — HTML inválido, um `<form>` nunca pode conter outro (o navegador descartaria o aninhamento, ou o submit de uma linha filha dispararia o `<form>` errado). Corrigido reestruturando o componente: o `<form>` pai fecha logo após o botão "Salvar", e o grupo de views aninhadas vive como IRMÃO dele, dentro de um `<div data-testid="edit-view-container">` envolvente. Teste dedicado adicionado (`"nunca desenha <form> aninhado"`) antes de declarar a subtarefa concluída.
4. **Falso positivo de ambiente durante a verificação final** (não uma lacuna de produto): `go test ./...` mostrou 5 falhas em `internal/platform/database` (`TestWithTenant_*`, `relation "probe" does not exist`) — esse pacote não foi tocado por GO-051. Investigação confirmou que o teste exige um fixture manual documentado no README (schemas `acme`/`beta` com uma tabela `probe`) que nunca tinha sido criado no container Postgres descartável desta rodada (`saltcorn-go051-pg`); reproduzido também num banco totalmente novo no mesmo container, confirmando que não era poluição de execuções anteriores. A PRIMEIRA tentativa de criar o fixture via `docker exec ... psql <<'SQL'` (sem `-i`) produziu sucesso aparente (sem erro, sem saída) mas NÃO executou nada — `docker exec` só encaminha stdin com a flag `-i`, um detalhe do próprio Docker, não do Postgres. Corrigido usando `docker exec -i`; com o fixture de fato aplicado, `go test ./internal/platform/database/...` passou (confirmado num banco novo E no banco principal usado pelo resto da suíte).

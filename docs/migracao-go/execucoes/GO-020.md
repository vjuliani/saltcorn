### Nota de escopo (decisões de design, fixadas antes/durante a implementação)

1. **GO-020 depende, na prática, de GO-019 — mesmo sem estar listado em `TASKS.md`.** `TASKS.md` lista GO-012/013/018 como dependências de GO-020, mas o escopo desta tarefa ("separar metadados e regras de views no Go") só faz sentido em cima de ALGUMA persistência de view — e `internal/views` (GO-019) já é essa persistência, mergeada em `master` (PR #22) antes desta tentativa começar. Reescrever uma segunda persistência de view seria duplicação, não separação de responsabilidades. Reaproveitado, documentado aqui como uma lacuna real do backlog (a lista de dependências de GO-020 em `TASKS.md`/`tasks.csv` deveria incluir GO-019 — corrigido nesta entrega).
2. **Escopo de "runtime de views" desta tarefa: só o viewtemplate "List", com colunas de campo direto.** `models/view.ts`/`base-plugin/viewtemplates/list.ts` (legado) somam mais de 3000 linhas cobrindo 8 viewtemplates nativos (List/Show/Edit/Feed/Filter/ListShowList/Room/WorkflowRoom, matriz GO-001 §2.3), dezenas de opções de exibição (`default_state`, ~40 flags só em List), tipos de coluna (Field/JoinField/ViewLink/Link/Action/Aggregation/Text/DropdownMenu) e fieldviews de célula plugáveis. Portar tudo isso de uma vez não é um recorte executável nesta tarefa. `internal/views/render.go` (novo) implementa a fatia mínima E REAL que prova o mecanismo de ponta a ponta: `template = "List"`, colunas `{type: "Field", field_name}` (o MESMO shape que `list.ts:1009,1055,1114,1723` já usa em produção — não um formato inventado), e um subconjunto fechado de `default_state` (`_order_field`, `_descending`). Qualquer view fora desse subconjunto é classificada como incompatível — nunca uma tentativa de renderização parcial (ver nota 4).
3. **Reaproveita GO-012/013/015 por inteiro — nenhuma consulta nova.** `views.CompileListPlan` delega a `records.Rows` (o mesmo compilador de consultas já testado) para buscar as linhas — a "regra de execução" nova é só "quais colunas mostrar e em que ordem", não uma segunda forma de consultar o banco. A autorização da TABELA (`identity.CanRead` sobre `MinRoleRead`, GO-015) e da VIEW (`identity.CanRead` sobre `MinRole`, GO-019) são checagens independentes, ambas sempre aplicadas — publicar uma view nunca contorna o papel mínimo de leitura da tabela por baixo.
4. **"Layouts incompatíveis bloqueiam publicação ou seguem rota legada explícita" (critério de aceite) — as duas metades, implementadas assim:**
   - **Bloqueiam publicação:** `views.CreateView`/`UpdateView` (GO-019, estendidos aqui) recusam qualquer transição em que o `min_role` resultante deixe de ser admin-only (`identity.RoleAdmin`) se o layout não passar em `ClassifyView` — `*UnsupportedLayoutError` com o motivo específico, 422 na camada HTTP. Editar mantendo a view admin-only nunca é bloqueado (um admin pode iterar livremente antes de publicar).
   - **Rota legada explícita:** o frontend (`ViewsListPage.tsx`) apresenta o motivo específico (`ViewUnsupportedError`, propagado do 422 do Go) e aponta para "administre pelo sistema atual" — não tenta desenhar uma tabela parcial/quebrada. Não há hoje um link cruzado de sessão entre o shell novo e o admin legado (nenhuma tarefa anterior estabeleceu esse contrato); documentado como limitação desta entrega, não fabricado.
5. **Achado de arquitetura (não bloqueador desta tarefa, registrado para decisão futura): colisão de nome de tabela entre `internal/views` (Go) e o legado.** `internal/views/schema.go` (GO-019) cria `_sc_views` com um shape PRÓPRIO (`id, name, table_id, template, min_role, configuration, created_at`) — mas o legado (`packages/saltcorn-data/db/reset_schema.ts:112-122`) já usa `_sc_views` no MESMO schema por tenant, com um shape DIFERENTE e incompatível (`viewtemplate` em vez de `template`, sem `created_at`, com `on_root_page`/`on_menu`/`default_render_page`/`exttable_name`/`description`/`attributes`, `min_role` com FK para `_sc_roles`). ADR-0004 confirma que Go e o legado operam sobre o MESMO Postgres, schema por tenant (`"tenant"."tabela"`) — não bancos separados. Enquanto todo teste desta migração usa schemas sintéticos e descartáveis (nunca um schema onde as migrations REAIS do legado já rodaram), isso não quebra nada hoje — mas um corte real de `tables.views` (ADR-0006/0008) para um tenant com histórico legado colidiria: `CREATE TABLE IF NOT EXISTS` seria um no-op sobre a tabela legada já existente, e todo INSERT/SELECT de `internal/views` falharia por coluna inexistente (`template` não existe; existe `viewtemplate`). **Recomendação, não implementada aqui** (fora do escopo desta tarefa, que é o runtime de renderização): antes de qualquer corte real da capacidade `tables.views`, `internal/views` precisa migrar para o shape real do legado (ou um ADR precisa decidir uma tabela com nome distinto, ex. `_sc_go_views`, com um script de migração de dados). Mesma classe de achado que `internal/metadata` (GO-011) já corre um risco menor (`_sc_tables`/`_sc_fields` também colidem por nome, mas com um shape mais próximo — não auditado a fundo nesta tarefa, fora de escopo).
6. **"Aplicar SB Admin 2 à interface administrativa" — uma página real, não só um demo isolado.** GO-018 já entregava o Shell/Sidebar/Topbar, mas `App.tsx` só demonstrava o `BuilderPanel`/`EditorPage` via botões ad-hoc, nunca uma página de dados de verdade. `ViewsListPage.tsx` (novo) é essa primeira página real: lista views via `GET /api/bff/views` (novo, GO-020) e pré-visualiza via `GET /api/bff/views/:id/render` (novo), com `ListView.tsx` reaproveitando as MESMAS classes CSS de `packages/saltcorn-markup/table.ts` (`table table-sm`, `table-hover` — GO-020 confirmou essas classes por leitura direta do código legado, não inventadas). **Limitação explícita:** a sidebar (`Sidebar.tsx`, GO-018) ainda renderiza `<a href>` reais, sem roteador client-side — o item de menu "Views" existe na estrutura de dados (documentação da rota real) mas quem efetivamente abre `ViewsListPage` nesta entrega é um botão de demonstração em `App.tsx`, o mesmo padrão já usado para `BuilderPanel`/`EditorPage`. Roteamento real do shell é GO-021 (ver README do frontend, nota já registrada em GO-018).
7. **"Aplicações fixture renderizam ... com paridade funcional" — validado via HTTP real, não navegador.** Confirmado em GO-018: sem ferramenta de browser neste ambiente. `TestRenderListHandler_PublishedViewRendersRealRows` (novo) é o oráculo: cria uma tabela "books" real (mesmo nome de fixture usado pela suíte legada `packages/saltcorn-data/db/fixtures.ts`, citada na matriz GO-001 como referência de correção), insere registros reais via `internal/records.CreateRecord` (GO-013, já testado), publica uma view List compatível, e confirma que o DTO de renderização devolve exatamente essas linhas, na ordem certa, com paginação funcionando — para os dois papéis (admin e público), a "paridade funcional" mais rigorosa alcançável sem navegador.

1. **`internal/views/commands.go`, bloqueio de publicação (domínio):** desabilitada a checagem `if minRole != identity.RoleAdmin { ... }` em `CreateView`/`UpdateView` (`if false && ...`). `TestUpdateView_PublishBlocksIncompatibleLayout` falhou (`erro = <nil>, esperado *UnsupportedLayoutError`). Restaurado, suíte volta a passar.
2. **`cmd/server`, bloqueio de publicação (HTTP):** mesma alteração. `TestUpdateViewHandler_PublishBlocksIncompatibleLayoutHTTP` falhou (`status = 200, corpo = {...min_role:100...}, esperado 422`) — a view teria sido publicada de verdade, incompatível. Restaurado.
3. **`internal/views/render.go`, classificação dentro de `CompileListPlan` (domínio):** desabilitado o `if err != nil { return ... }` logo após `ClassifyView` (`if false && err != nil`). `TestCompileListPlan_UnsupportedTemplateRejected` falhou (`erro = <nil>`). Restaurado.
4. **`cmd/server`, mesma alteração, nível HTTP — o achado mais grave:** `TestRenderListHandler_UnsupportedViewReturns422` falhou com `status = 200` e o corpo continha as TRÊS linhas reais da tabela "books" (`{"rows":[{"title":"Dune",...},...]}`) para uma view do tipo "Show" — ou seja, sem a checagem, o endpoint de renderização vazaria dados de uma view fora do subconjunto suportado, silenciosamente, com 200 OK.

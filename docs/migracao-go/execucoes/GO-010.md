- **Nota de escopo (decisão de design registrada em ADR-0009):**
  - Sem SDK externo (nem OpenTelemetry, nem cliente Prometheus) — `log/slog` (biblioteca padrão) para logs, formato de exposição de texto do Prometheus escrito à mão para métricas, e o padrão W3C Trace Context (header `traceparent`) para correlação entre runtimes. Justificativa: mesmo cuidado de custo de dependência já tomado com pgx/jwt/otp, e ausência de um coletor real (Prometheus/Jaeger) neste ambiente para validar a integração de um SDK completo contra ele.
  - "RPC" do escopo ("HTTP/SQL/jobs/RPC"): não existe hoje uma camada RPC binária separada — a comunicação entre BFF (GO-017, não implementado) e o backend Go é HTTP/JSON (ADR-0003); `telemetry.Middleware` aplicado à API interna HTTP cobre essa comunicação hoje. Quando o host de plugins JS (GO-022, RPC de verdade) existir, deve reusar os mesmos primitivos, não inventar um mecanismo próprio.
  - `/healthz`/`/readyz` deliberadamente NÃO instrumentadas — probes de alta frequência virariam ruído de log/métrica sem valor de diagnóstico.
  - Redação de dados sensíveis: por NOME de atributo no handler de log (não por conteúdo/regex) — cobre o caso dominante de forma previsível. Para SQL especificamente, `internal/platform/database` nunca loga texto de consulta, parâmetros ou a mensagem crua do driver (que pode ecoar valor de linha em mensagens de violação de constraint) — só um resultado classificado (`ok`/`error`/`canceled`/`deadline_exceeded`).
  - Controle de cardinalidade: toda métrica declara seu conjunto de labels uma vez, na criação — nenhuma métrica usa tenant/ator/path bruto como label; essa granularidade fica nos logs (via `telemetry.LoggerFor`), que não sofrem o mesmo problema de explosão de séries temporais.

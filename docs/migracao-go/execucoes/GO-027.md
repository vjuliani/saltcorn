### Decisões de escopo (preflight)

1. **O Pack Go só cobre entidades que JÁ existem como catálogo real no backend Go**: tabelas/campos (GO-011), views (GO-019/020), triggers (GO-024), triggers agendados (GO-025), biblioteca e config (novos nesta tarefa). O Pack do legado (`packages/saltcorn-admin-models/models/pack.ts`) também carrega pages/page_groups/roles/tags/models/model_instances/event_logs/code_pages — confirmado por investigação de preflight que NENHUMA dessas entidades tem catálogo Go ainda (páginas nunca foram portadas; roles são papéis FIXOS por constante `identity.RoleAdmin`/`RolePublic`, não um catálogo dinâmico de papéis nomeados). Um Pack só pode conter o que o backend Go sabe recriar de verdade — mesma disciplina de "subconjunto prioritário" de toda a série de tarefas.
2. **`Pack.Version` é um campo NOVO — o legado não tem nenhum campo de schema versionado.** Confirmado por grep completo no monorepo (achado de preflight): compatibilidade entre versões de pack no legado é best-effort, campos ausentes viram zero-value silenciosamente. `Import` recusa explicitamente uma versão futura desconhecida (`ErrUnsupportedVersion`) — nunca tenta importar pela metade um formato que não entende.
3. **"Faltas de plugin/versão são reportadas antes de aplicar alterações" é uma GARANTIA NOVA, não uma porta de comportamento existente** — confirmado por investigação de preflight: `can_install_pack` do legado só verifica conflito de tipo de campo entre tabela existente e a do pack, view colidindo com tabela diferente, e campo obrigatório novo em `users` — TUDO como aviso (warning), nunca bloqueio; NÃO existe checagem de plugin/versão no legado. Pior: `install_pack` continua instalando o resto do pack mesmo quando um plugin falha ao carregar via `loadAndSaveNewPlugin` (só `console.error` dentro de um try/catch que segue em frente). GO-027 constrói isto do zero: `Validate` roda ANTES de qualquer mutação de catálogo, devolvendo TODAS as ausências de uma vez (não uma por vez).
4. **Sem inventário real de plugins de terceiro neste checkout** (achado repetido desde GO-001/003/004, reconfirmado): `availablePlugins` (nome → versão) é sempre fornecido explicitamente por quem chama `Import` — `Validate`/`Import` nunca descobrem plugins instalados sozinhos, não há nada real para descobrir.
5. **Atomicidade "tudo ou nada" herdada da convenção já estabelecida desde GO-013, não reinventada**: `Import` roda inteiro dentro da MESMA transação que o chamador controla — qualquer erro propaga imediatamente (divergência deliberada do legado, que continua tentando instalar o resto mesmo com falhas), e o `db.WithTenant` do chamador desfaz TUDO. Nenhum mecanismo de transação novo foi construído — só a disciplina de nunca fazer commit parcial dentro de `Import` em si.
6. **Duas fases de criação de tabela** (todas as tabelas sem campos primeiro, depois todos os campos de todas as tabelas): necessário para que um `FieldKey` referencie QUALQUER tabela do mesmo pack, incluindo uma declarada DEPOIS dela no array, ou uma referência circular entre duas tabelas — um export real de uma aplicação com relações não garante nenhuma ordem topológica particular entre tabelas. Confirmado por regressão deliberada (ver "Achado de verificação").
7. **Referências entre entidades por NOME, nunca por ID interno** — mesma convenção do legado (Pack é portável entre tenants/instalações, onde IDs internos nunca coincidem). `internal/metadata.AddField` já resolve `FieldDef.References` (nome) para o ID da tabela internamente (comportamento pré-existente desde GO-011, confirmado por leitura direta do código antes de escrever `Import`) — nenhuma resolução de nome nova precisou ser inventada para campos, só reaproveitada.
8. **`internal/config` é deliberadamente UNTYPED** — o subconjunto prioritário necessário para `Pack.Config` fazer round-trip sem perda, não o catálogo TIPADO completo do legado (`models/config.ts`, ~2140 linhas, ~40+ chaves com validação por tipo: site_name, timezone, smtp_*, menu_items, etc.). Portar o catálogo tipado inteiro é maior que o necessário para esta tarefa — fica para uma tarefa futura dedicada. Não confundir com `internal/platform/config` (configuração do PROCESSO Go, variáveis de ambiente) — `internal/config` é configuração da APLICAÇÃO dentro de um tenant.
9. **`internal/library` não resolve slots em runtime** — `Library.resolveSegment` do legado (substituir um segmento `{type:"library"}` pela definição real durante a renderização de uma view, com proteção contra ciclo de auto-referência) é responsabilidade de GO-020 (runtime de views), não de import/export. Este pacote só guarda e devolve o layout como JSON opaco, exatamente como `library_pack()` do legado faz.
10. **Extensões aditivas, não rewrites, em pacotes já mergeados**: `internal/metadata.ListTables`, `internal/triggers.ListAll`, `internal/scheduler.ListAll` são funções NOVAS que reaproveitam o padrão de listagem já existente (`ListFields`/`TriggersFor`/`DueTriggers`) — nenhum contrato existente foi alterado, só uma consulta "todas as linhas" adicionada onde só existia "filtrado por X".
11. **Loja remota de packs (`packs_store_endpoint`, fetch HTTP) fica fora de escopo** — dependência de rede contra um serviço de terceiro que não existe neste checkout, sem exercício possível no piloto, mesma disciplina de "sem inventário real" aplicada a plugins de terceiro.
12. **Sem wiring de rotas HTTP em `cmd/server`** — testado e provado no nível de pacote (`internal/pack.Export`/`Import`), mesma decisão de escopo já aplicada por GO-023/024/026 para seus próprios mecanismos.
13. **Verificação de regressão deliberada, dois pontos**: (a) desabilitar o gate de `Validate` em `Import` — uma dependência de plugin ausente deixa de impedir a criação de entidades; (b) colapsar a criação de tabela+campos para uma única fase — um pack com uma tabela referenciando outra declarada DEPOIS dela no array passa a falhar de verdade (`FieldDef.References não encontrada`).

### Achado de verificação (regressão deliberada, dois pontos + um bug de fixture)

1. **Gate de `Validate` em `Import` (`internal/pack/import.go`)**: trocado `if missing := Validate(p, availablePlugins); len(missing) > 0` por `if missing := Validate(p, availablePlugins); false && len(missing) > 0`, desabilitando o bloqueio. `TestImport_MissingPlugin_ReportsBeforeApplying_NothingCreated` falhou com `"err = <nil>, esperado *MissingDependenciesError"` — confirmando que, sem o gate, a tabela `orfa` seria REALMENTE criada apesar da dependência de plugin `stripe-payments` estar ausente. Restaurado, suíte volta a passar.
2. **Duas fases de criação de tabela (`internal/pack/import.go`, `Import`)**: colapsado o laço de criar tabelas e o laço de adicionar campos num ÚNICO laço (criar tabela e imediatamente seus campos, como uma implementação ingênua faria). `TestImport_ForwardTableReference_TwoPhaseFieldCreation` (novo teste desta tarefa: tabela "posts" com `FieldKey` para "people", declarada DEPOIS no array) falhou com `"pack: adicionar campo \"posts\".\"author\": metadata: tabela referenciada (FieldDef.References) não encontrada"` — confirmando que a ordem de declaração no array realmente importaria sem a separação em duas fases. Restaurado, suíte volta a passar.
3. **Bug real de fixture de teste (não de produção), encontrado durante a escrita dos testes**: os testes originais usavam sufixos de tenant com hífen (`"version-mismatch"`, `"future-version"`) combinados com nomes de função de teste longos, criando o schema via `pgx.Identifier{string(tenant)}.Sanitize()` sobre a string BRUTA — enquanto `database.WithTenant` resolve o schema internamente via `tenancy.SchemaName(t)`, que REMOVE (não substitui por `_`) caracteres não-identificador. Para nomes curtos, as duas formas nunca divergiam; para os nomes longos desta suíte, a truncagem de 63 bytes do Postgres cortava a string COM hífen e a string SEM hífen em pontos DIFERENTES do texto, produzindo dois nomes de schema DIFERENTES — a criação (`CREATE SCHEMA`) usava um, e a resolução de `WithTenant` (`SET LOCAL search_path`) usava outro, nunca criado, dando `ERROR: no schema has been selected to create in (SQLSTATE 3F000)`. Corrigido aplicando `tenancy.SchemaName` na CONSTRUÇÃO do nome do tenant de teste (`fixture_test.go`), garantindo que o helper de fixture usa exatamente a mesma string que `WithTenant` resolve — elimina a divergência pela raiz, não só evitando hífens nos sufixos de teste.

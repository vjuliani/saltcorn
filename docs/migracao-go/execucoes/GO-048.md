## Preflight — levantamento e decisões de escopo

Delegado a um subagente de pesquisa (sem escrita de código) cobrindo: (1) o editor legado (`packages/workflow-editor`, React Flow); (2) o motor Go correspondente (`internal/workflow`); (3) o frontend novo já existente; (4) o BFF. Achados centrais:

1. **Gap principal, não previsto no texto original da task**: `internal/workflow` (GO-024) só tem estado de EXECUÇÃO persistido (`_sc_workflow_runs`/`_sc_workflow_trace`) — a `Definition` (grafo de passos) é montada em código Go compilado, nunca lida de uma tabela. O comentário do próprio pacote já dizia isso explicitamente: *"um catálogo persistido de definições de workflow, se necessário, é escopo de uma tarefa futura"*. Sem uma definição persistida, o Aceite de GO-048 ("um usuário cria/edita um workflow visualmente... e o resultado é executado de ponta a ponta por `internal/workflow`") é logicamente impossível de cumprir. **Decisão**: esta task absorve esse trabalho de backend (schema + CRUD + `Compile`) antes de qualquer UI — uma expansão de escopo real e necessária, não tangencial, documentada aqui em vez de silenciosamente ignorada.
2. **`Workflow` é uma tabela PRÓPRIA (`_sc_workflows`), não uma reutilização de `_sc_triggers`** — o legado hospedava workflows num `Trigger` com `when_trigger` "API call"/"Never" (independente de tabela); o catálogo Go de triggers (GO-024) exige `table_id NOT NULL`, um conceito que não existe hoje. Inventar um "trigger sem tabela" no schema de triggers seria uma mudança maior e mais arriscada do que criar uma tabela nova e pequena.
3. **Ramificação binária (`Next`/`Else` conforme `OnlyIf`), nunca a expressão N-vias livre do `next_step` do legado** — o motor Go (`run.go`, decisão já tomada em GO-024) só executa a forma binária; o editor visual nunca deveria oferecer uma condição que o motor não executa de verdade.
4. **Catálogo de ações restrito a `set_context` (efeito interno puro) e `count_rows` (leitura pura de uma tabela do tenant)** — `send_email`/`webhook` (o catálogo de `internal/triggers`, GO-029) ficam FORA: `StepFunc` recebe só `(ctx, tx, wfContext)`, sem `runID`; a chave de idempotência do enfileiramento em `internal/notify` precisa ser única POR EXECUÇÃO (duas execuções concorrentes do mesmo workflow, mesmo estado de contexto, não podem colidir na mesma chave), e derivar isso sem `runID` exigiria injetar um token sintético só para essa finalidade — complexidade não exigida pelo Aceite, que não depende de efeito externo observável.
5. **Candidatos excluídos do escopo por serem desproporcionais ao Aceite** (mesma disciplina de "divergência deliberada" das tasks anteriores): geração de workflow por IA (`copilot_generate_workflow`, plugin+LLM — nenhuma integração de LLM existe no backend Go hoje, mesma razão de GO-047); workflow como ação de outro workflow (sub-workflow — já excluído explicitamente em GO-024); o catálogo de ~14 ações builtin + ações de plugin do legado além de `set_context`/`count_rows`; tipos de passo que pausam execução (`UserForm`, `WaitUntil`, etc. — sem suporte a status "Waiting" no motor Go, documentado como lacuna de CAP-051); um node type dedicado a `ForLoop` com handles especiais (o motor já suporta loop nativamente via uma aresta comum apontando para um passo anterior).
6. **Frontend**: nenhuma biblioteca de grafo estava instalada; nenhuma infraestrutura de formulário dinâmico (`showIf`/Monaco) existe no pacote novo — decisão de usar `@xyflow/react` (sucessor mantido do React Flow) + painel lateral nativo escrito à mão (viável dado o catálogo de só 2 ações).
7. **BFF**: nenhuma rota de workflow existia — proxy completo a construir do zero, mesmo padrão de `tables`/`views`.

### Regressões deliberadas (uma por camada)

1. **Go (`internal/workflow.UpdateStep`)**: trocar `WHERE id = $9 AND xmin::text = $10` por `WHERE id = $9 AND ($10 = $10)` (condição sempre verdadeira, mas ainda usando o parâmetro) → o teste de conflito de versão de PASSO (adicionado nesta mesma verificação, pois não existia antes — só `UpdateWorkflow` tinha esse teste) falha de verdade: `UpdateStep com versão obsoleta erro = <nil>, esperado ErrVersionConflict` → restaurado → volta a passar. **Achado colateral**: a lacuna de cobertura em si (nenhum teste cobria conflito de versão em `UpdateStep`) foi encontrada e corrigida ANTES da regressão confirmar o bug — a regressão só teve efeito depois do teste novo existir.
2. **BFF (`app.ts`, rota `runWorkflow`)**: acrescentar `+ Math.random()` ao escopo da `computeIdempotencyKey` de `/run` (uma tentativa inicial com `+ Date.now()` não produziu falha — duas chamadas em sequência rápida caem no mesmo milissegundo) → `duas vezes com o mesmo corpo não inicia dois runs` falha de verdade: `1 !== 2` (dois runs criados) → restaurado → volta a passar.
3. **Frontend (achado real, não uma regressão introduzida deliberadamente — descoberto DURANTE a escrita dos testes)**: `workflow?.steps ?? []` cria uma referência de array NOVA a cada render enquanto nenhum workflow está selecionado; como esse valor alimentava o `useMemo` de `nodes` (dependência `[steps, ...]`), o memo recalculava a cada render, refazendo um `useEffect` de sincronização com `renderedNodes` a cada render — um ciclo `render → useMemo → useEffect → setState → render` sem fim. Confirmado via instrumentação de contagem de render (escrita direta em arquivo para contornar o buffer de console do test runner): ~2000 renders em 8 segundos antes do timeout do teste, consumindo 100% de um núcleo indefinidamente. Corrigido com uma constante `EMPTY_STEPS` estável em nível de módulo. **Regressão de confirmação**: reintroduzir `workflow?.steps ?? []` faz a MESMA suíte travar de novo (verificado antes de decidir a correção final).

### Achados reais de bootstrap/produção corrigidos durante a execução (não são bugs de produto do motor em si — são lacunas de provisionamento)

1. **`cmd/cli/e2eseed.go` e as fixtures HTTP de `cmd/server` (`records_test.go`) não chamavam `workflow.EnsureSchema`** — mesma classe de achado já vista em GO-040 (`triggers.EnsureSchema`), GO-045 (`outbox.EnsureSchema`) e GO-047 (`config.EnsureSchema`). Corrigido proativamente por inspeção, antes de qualquer teste revelar a lacuna via falha.
2. **`cmd/cli/e2eseed.go` registrava ownership de Go (`cutover.SetOwner`) só para `["tables.records", "tables.schema", "tables.views"]`** — a nova capability `"workflows"` (`workflowsCapability` em `main.go`) não estava na lista. `cutover.Guard` falha FECHADO por padrão (valor zero do owner nunca é igual a `OwnerGo`) — toda rota de workflow devolvia `409` imediatamente (`duration_ms:0`, sem sequer chegar ao handler) no primeiro run do E2E completo. Corrigido acrescentando `"workflows"` à lista; confirmado por evidência de falha genuína (409 nos logs do backend Go) ANTES da correção, e por sucesso (200/201 em toda a sequência) DEPOIS.
3. **Achado de TESTE (não do produto) no fixture do próprio `workflow.spec.ts`**: as duas chamadas de criação de registro usavam corpo idêntico (`{}`), colidindo na `Idempotency-Key` determinística do BFF (`computeIdempotencyKey` a partir de ator+tenant+tabela+CORPO — mesmo mecanismo, mesmo propósito, de `createView`/`updateView`/`runWorkflow`) — a segunda chamada era tratada como retry da primeira, criando só 1 registro em vez de 2. `count_rows` corretamente contou 1, não 2 — o teste esperava o número errado. Corrigido dando aos dois registros um campo com valor distinto.

2. **Correção de comportamento herdado de GO-020: a fonte de verdade de List é `configuration.columns[]`, não `configuration.layout.besides[]`.** `internal/views/render.go` (GO-020) lia `layout.besides[].contents.type` esperando o literal capitalizado `"Field"` — mas o pack real mostra que `layout.besides[].contents.type` é sempre MINÚSCULO (`"field"`/`"join_field"`/`"action"`) no formato realmente produzido pelo builder legado reaproveitado (GO-018); o literal capitalizado só existe na lista FLAT paralela `configuration.columns[]`, que é exatamente o que `packages/saltcorn-data/base-plugin/viewtemplates/list.ts:1009` (`get_state_fields`) lê para decidir dados — `layout` é só a árvore de arranjo VISUAL, nunca a fonte de dados. Confirmado lendo o `list.ts` legado diretamente. Isso significa que a implementação de GO-020, embora correta contra seus próprios testes (fixtures sintéticas com o formato errado), NUNCA teria classificado corretamente uma view List real produzida pelo builder de produção. Corrigido: `classifyListColumns`/`classifyShowColumns`/`classifyEditColumns` agora leem `configuration.columns[]` (flat, capitalizado) para os três templates — mais simples que percorrer a árvore recursiva de `layout`, e verificado corretamente contra os 9 `columns[]` reais do pack `guitars`. Testes/fixtures que assumiam o formato antigo (`internal/views/classify_test.go`, `cmd/server/{views,render}_test.go`) foram corrigidos para o formato real, não apenas ajustados para a nova API.
3. **Achado real, corrigido (não do escopo de views): `internal/records.validateFieldValues` nunca aceitava um valor de campo `FieldInteger`/`FieldKey`/`FieldDate` vindo de um corpo JSON HTTP.** `encoding/json` decodifica todo número como `float64` (nunca `int`) e toda data como `string` (nunca `time.Time`); `validateValue` exige exatamente `int/int32/int64` e `time.Time`. Nenhum teste HTTP anterior a esta tarefa exercitava um campo não-texto via `records.CreateRecord`/`UpdateRecord` (confirmado: `TestCreateRecordHandler_Success` só usa o campo de texto `"label"`) — ou seja, ESCREVER um registro com um campo inteiro/chave/data pela API HTTP real estava quebrado desde sempre, só nunca tinha sido exercitado. Corrigido com `coerceJSONValue` (novo, `internal/records/commands.go`), chamado dentro de `validateFieldValues` antes de validar — converte `float64` sem parte fracionária para `int64` (campos integer/key) e `string` RFC3339 para `time.Time` (campos date), preservando o erro `ErrTypeMismatch` para qualquer valor que não seja um desses formatos. Sem esta correção, Edit (GO-039) não conseguiria salvar nenhum campo `select` (key) nem `flatpickr` (date) via HTTP — o que descreveria a maioria dos campos do pack `guitars`.
4. **Carve-out para GO-051: renderização de view aninhada.** `create_guitar` (Edit) tem, dentro de `layout.above`, um nó `{"type": "view", "view": "edit_processed_embed", "relation": ".guitars.processed$guitar"}` — isto é, a view INTEIRA `edit_processed_embed` é renderizada embutida dentro de `create_guitar`, filtrada pela relação 1:N entre `guitars` e `processed`. Implementar isso com o rigor que o resto desta migração exige (testes de autorização, tenant, ciclo) não cabe dentro do orçamento desta task sem comprometer a qualidade das outras 8 views. Decisão: fora de escopo, registrado como GO-051.

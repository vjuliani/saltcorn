Preflight delegado a um subagente de pesquisa (read-only) cobrindo os 4 CAP citados no escopo da task (CAP-078/079/080/081/083) contra o legado e o estado atual do backend Go. Achados centrais:

1. **`_sc_metadata` não existe hoje** — não confundir com `_sc_metadata_version` (contador de invalidação de cache do catálogo de tabelas/campos, dentro de `internal/metadata`, um conceito totalmente diferente e homônimo por acidente).
2. **GO-032 já construiu um backup de instalação completo genuíno** (`internal/installation/backup.go`: `pg_dump --format=custom` do banco INTEIRO + árvores `files/`/`plugins/`/`sqlite/`, manifesto com hash SHA-256 por arquivo) — isto já SUPERA a cobertura de uma lista literal de entidades (Plugin/Role/Page/PageGroup/MetaData/File/Crash/Table/View/Field): um dump completo nunca esquece uma tabela nova, ao contrário de uma lista curada e estática. O que falta de verdade é agendamento/retenção/criptografia/destinos remotos (CAP-081).
3. **Catálogo de plugins já existe em forma mínima** (`_sc_plugin_versions`, nome+versão, GO-032) — falta GOVERNANÇA: validação de versão, compatibilidade de engine, auditoria de upgrade.
4. **`internal/notify` é inteiramente texto puro** (comentário do próprio código já registrava isso como decisão explícita de GO-026) — zero suporte a HTML.
5. **`internal/pluginhost` (GO-022) é só o mecanismo de EXECUÇÃO** (processo isolado rodando JS) — nunca um catálogo/registro de plugins instalados; a distinção entre "executar" e "governar" plugins, citada no próprio texto do escopo da task, é real e já estava correta.

**Decisões de escopo tomadas (nenhuma "sem porte real" ficou sem decisão registrada, conforme o Aceite):**

- **Descoberta via registro npm remoto (`npm-registry-fetch` do legado) fica FORA de escopo.** Não existe, neste checkout, nenhum plugin de terceiro real para validar contra um registro — mesmo achado já repetido desde GO-001/003/004/029. Adicionar uma dependência de rede a uma ferramenta administrativa OFFLINE (`internal/installation` nunca faz chamada de rede hoje) sem nenhum consumidor real para testar seria especulativo.
- **Compatibilidade de engine é 100% LOCAL**: lê `engines.saltcorn` de `package.json` (já presente no diretório do plugin) e compara contra `PluginEngineVersion` (constante que este backend Go declara) — sem round-trip de rede.
- **Checagem de "views dependentes antes de remover um plugin" é DELIBERADAMENTE VAZIA.** Hoje todo viewtemplate (List/Show/Edit/Feed) é NATIVO do backend Go (GO-020/039/051) — nenhum plugin de terceiro jamais registrou um viewtemplate, tipo de campo ou fieldview (`internal/pluginhost` só executa expressão/ação em processo isolado). Não existe, portanto, nenhum caso real em que remover um plugin poderia quebrar uma view — construir uma checagem que nunca pode encontrar uma dependência real seria trabalho de fachada, reservado para quando (se) plugins-de-terceiro-com-viewtemplate existirem de verdade.
- **Backup de instalação completa (CAP-080) não foi reconstruído** — já está corretamente coberto por GO-032, e de forma SUPERIOR à lista literal de entidades do legado (ver achado 2 acima). `Page`/`PageGroup`/`Crash` não têm equivalente Go (gaps já conhecidos de tasks anteriores); `Role` não é uma entidade de DADOS no backend Go (é um `RoleID` de conjunto fechado, GO-008) — não haveria linha nenhuma para copiar mesmo se quiséssemos.
- **Destinos remotos de backup (S3/SFTP) ficam FORA de escopo.** Sem credenciais nem infraestrutura de teste neste checkout para validar contra um provedor de armazenamento real — simular sucesso sem essa prova violaria a disciplina desta sessão de nunca fingir uma capacidade não realmente testada.
- **Retenção GFS e criptografia de backup são construídas de verdade** — nenhuma razão de escopo as exclui (são puramente locais, testáveis sem dependência externa).
- **Nenhum motor MJML** (linguagem de template intermediária do legado, compilada por um pacote npm dedicado) — sem equivalente Go, e portar um motor de template inteiro para um caso de uso de e-mail administrativo simples seria desproporcional. `RenderShowPlanEmailHTML` produz HTML final diretamente (tabela rótulo/valor, inline-styled), cobrindo literalmente o Aceite ("ao menos um modo de e-mail HTML a partir de View funciona").
- **A ação de trigger `send_email` (`internal/triggers`) NÃO foi estendida** para aceitar uma view — `internal/triggers` permanece `pgx.Tx`-only e explicitamente fora do escopo desta task (mesma fronteira que GO-041/GO-055 já delimitaram); o mecanismo de e-mail HTML a partir de View vive em `internal/notify`+`internal/views`, composável por qualquer chamador futuro, sem exigir essa conversão.

### Regressões deliberadas (uma por mecanismo de segurança/integridade realmente construído)

1. **Go (`internal/installation/retention.go`, `ApplyRetention`)**: remover a semente `kept := map[string]bool{sorted[0].Name: true}` (rede de segurança "sempre mantém o mais recente") → `TestApplyRetention_AlwaysKeepsMostRecent` falha de verdade (`keep=[]`, o único ponto de recuperação seria apagado com qualquer política restritiva ou zerada) → restaurado → suíte de retenção volta a passar.
2. **Go (`internal/installation/plugins.go`, `validatePluginVersions`)**: descartar o resultado `ok` de `engineCompatible` (só propagar erro de parsing, nunca o de incompatibilidade) → `TestSyncPlugins_RejectsIncompatibleEngine` falha de verdade (um plugin com `engines.saltcorn` incompatível seria registrado silenciosamente) → restaurado → suíte de plugins volta a passar.
3. **Go (`internal/installation/crypto.go`, `decryptFile`)**: ignorar o erro de `gcm.Open` (autenticação do AES-GCM) → `TestDecryptFile_WrongPassphraseFailsExplicitly` E `TestDecryptFile_TamperedCiphertextDetected` falham de verdade (senha errada ou ciphertext adulterado deixam de ser detectados) → restaurado → suíte de criptografia volta a passar.
4. **Achado real (não hipotetizado, encontrado por flakiness genuína)**: `internal/installation/schedule.go`, `RunScheduledBackups` propagava "context canceled" como um ERRO FATAL sempre que o cancelamento do contexto (desligamento do processo, `SIGTERM` real em `cmd/cli backup-schedule`) acontecia enquanto um backup estava EM CURSO (a chamada de I/O de banco dentro de `Backup()` respeita `ctx` e retorna esse erro assim que cancelado). Descoberto rodando a suíte completa repetidamente sob carga real (não em isolamento) — `TestRunScheduledBackups_RunsImmediatelyAndOnEachTick` falhava ~40% das vezes com "RunScheduledBackups: context canceled". Corrigido verificando `ctx.Err() != nil` antes de propagar o erro de `runOneScheduledBackup`, tratando esse caso como desligamento gracioso (retorno nil) — nunca uma falha real (disco cheio, Postgres fora do ar, que teria acontecido de qualquer forma). Teste dedicado novo (`TestRunScheduledBackups_CancelDuringBackupIsGraceful`, 20 repetições) confirmado falhando genuinamente sem a correção (`context canceled` propagado) e passando de forma estável (8/8, depois 20/20) com ela.

### Achado real corrigido pelo CI (não capturado pela suíte Go local)

Os 3 checks obrigatórios que sobem uma release real (`local-howto`,
`docker-howto`, `install-upgrade-restore`) falharam no primeiro push do PR
com `installation: componentes da release incompatíveis` —
`CheckRelease` (`serve.go`) rejeitou a release recém-buildada.
Causa raiz: `migracao/distribution/manifest.mjs` tem sua PRÓPRIA cópia
hardcoded de `version`/`schema` (`'0.1.0-go032'`/`2`), completamente
desacoplada da constante Go `installation.Release`/`SchemaVersion` que
esta task bumpou para `"0.1.0-go046"`/`3` — nenhuma fonte única
compartilhada entre Go e este script Node existe. A suíte Go local nunca
exercitava esse arquivo (é só invocado por `migracao/distribution/
build.sh`, parte do pipeline de release, fora de `go test`), por isso a
divergência só apareceu nos checks de CI que constroem uma release de
verdade. Corrigido atualizando os dois literais em `manifest.mjs` para
bater com os novos valores, com um comentário novo documentando essa
sincronização manual necessária — confirmado localmente: `bash
migracao/distribution/build.sh` seguido de `CheckRelease` no diretório
gerado, PASS.

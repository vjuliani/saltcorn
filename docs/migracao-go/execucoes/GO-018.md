### Nota de escopo (decisões de design)

Tarefa de tamanho L, a maior até aqui — decisões fixadas explicitamente, com a investigação (agente de exploração dedicado, sem escrita de código) feita antes de qualquer linha de código:

1. **"Sem disputa de DOM" implementado como "nenhum script legado carregado", não como coexistência cuidadosa.** `packages/saltcorn-sbadmin2/index.js` monta sidebar/topbar como HTML e delega toda interatividade (collapse de submenu, toggle) a `bootstrap.bundle.min.js`/jQuery lendo `data-bs-toggle`/`data-bs-target`. `Sidebar.tsx`/`Topbar.tsx`/`Shell.tsx` portam a MESMA estrutura de dados (`MenuSection`/`MenuItem`, espelhando `sidebar()`/`sideBarItem()` do legado) e as MESMAS classes CSS (reaproveitando `sb-admin-2.min.css` sem alteração), mas a interação é `useState` — zero script de terceiro no DOM, logo nenhuma disputa possível. Os arquivos JS do tema (`bootstrap.bundle.min.js`, `jquery.easing.min.js`, `sb-admin-2.min.js`) foram deliberadamente EXCLUÍDOS da cópia de assets — só CSS/fontes/ícones foram copiados.
2. **Builder Craft.js integrado como widget imperativo isolado, não reimportado como árvore React.** `packages/saltcorn-builder` já é React (Craft.js), mas é uma árvore React DIFERENTE, com seu próprio bundle webpack (`dist/builder_bundle.js`, UMD, `window.builder`). Reimportar seus componentes para dentro da árvore React deste shell (bundlada por Vite) arriscaria duas cópias de React/conflito de bundler — exatamente o tipo de problema que ADR-0002 quer evitar. Em vez disso, `BuilderPanel.tsx` carrega o bundle UMD via `<script>` e chama `window.builder.renderBuilder(...)` — a MESMA função que páginas legadas já chamam hoje — numa `<div>` que o React deste shell nunca mais toca por dentro. Isso é "encapsular widgets imperativos" (ADR-0002) aplicado ao próprio builder.
3. **`builder_bundle.js` copiado do `dist/` já publicado, não reconstruído.** Rebuildar o builder (webpack) não é escopo desta tarefa (o código-fonte do builder não muda); a cópia estática é documentada como tal no README, com a instrução de quem alterar `packages/saltcorn-builder` também atualizar a cópia.
4. **Lacuna real descoberta: nenhum teste de round-trip existia para `layoutToNodes`/`craftToSaltcorn`** (`packages/saltcorn-builder/src/components/storage.js`) — o único teste do pacote (`relations_finder.test.js`) mocka `@craftjs/core` inteiro e testa outra coisa (descoberta de relações). Como o critério de aceite "round-trip preserva propriedades, referências e extensões" é justamente sobre essas duas funções, foi escrito `tests/storage_roundtrip.test.js` — com um `<Editor>` REAL do Craft.js (não mockado), aproveitando que `setup-node-runner.js` já fornece um ambiente jsdom global (descoberto lendo o próprio arquivo) — em vez de inventar uma forma de testar sem o Craft.js real, o que não provaria nada sobre o round-trip de verdade.
5. **Achado colateral, não corrigido (fora do escopo desta tarefa):** `packages/saltcorn-builder/tests/relations_finder.test.js` já falha (18/18 subtestes) mesmo sem nenhuma mudança desta tarefa — confirmado rodando o arquivo isoladamente antes de qualquer edição, e via `git status` mostrando que nenhum arquivo do pacote foi alterado além da adição do teste novo. Registrado aqui como achado, não escondido; não investigado a fundo nem corrigido porque é uma falha pré-existente e não relacionada ao escopo de GO-018 (shell React), corrigi-la seria escopo não pedido.
6. **Layout versionado:** `types/layout.ts` define um envelope `{version, layout}` — o que ADR-0002 pede como "documento de layout versionado". O formato da árvore em si (`above`/`besides`/`contents`) continua sendo o mesmo tipo `Layout` de `@saltcorn/types/base_types` (legado), não duplicado.
7. **Dependências de teste/build:** Vitest + React Testing Library (não `node:test` puro, ao contrário do BFF de GO-017) — justificado porque testar comportamento de componentes React (classes CSS dinâmicas, atributos ARIA, visibilidade) tem ferramentas maduras e específicas para isso; usar `node:test` cru aqui seria reinventar o que RTL já resolve corretamente. Vite como bundler (não webpack, ao contrário do resto do monorepo) — pacote novo e isolado, sem HMR/dev-server já configurado em nenhum `webpack.config.js` existente para reaproveitar.
8. **Vulnerabilidades de dependência de desenvolvimento (`npm audit`):** `esbuild`/`@vitest/mocker` têm avisos moderados, corrigidos só em Vite 8/Vitest 5 (upgrade maior, não validado nesta entrega). Ambos expõem apenas o servidor de desenvolvimento LOCAL (nunca o build de produção nem CI) — mantido na série atual (Vite 5.4.21/Vitest 2.1.9, as versões mais recentes DENTRO da faixa não-major), documentado no README como risco aceito, não escondido.
9. **Verificação visual em navegador real não foi possível neste ambiente** (sem ferramenta de browser/screenshot disponível) — a suíte de testes (jsdom + React Testing Library) cobre comportamento (classes, ARIA, visibilidade, ausência de scripts legados), e o servidor de desenvolvimento real foi iniciado e todos os assets confirmados servidos corretamente via `curl`, mas isso não substitui uma inspeção visual humana. Registrado explicitamente, não fabricada uma alegação de verificação visual que não ocorreu.

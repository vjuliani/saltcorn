### Nota de escopo (decisões de design, fixadas antes de codificar)

1. **Lacuna real descoberta: nem tabelas/campos (`internal/metadata`) nem "views" tinham qualquer exposição HTTP.** GO-017 wireou só registros (`internal/records`); `metadata.CreateTable`/`AddField` só eram chamados de dentro de testes Go. "Conectar tabelas, campos, views" (escopo desta tarefa) portanto exige, primeiro, fechar essa lacuna — não é possível "criar tabela e view" via BFF sem rotas Go reais para isso.
2. **"Views" não tem runtime de renderização ainda — isso é GO-020, não esta tarefa.** GO-020 ("Portar runtime de views e páginas") ainda é `TODO` e é quem vai separar metadados/regras de views e implementar a renderização React de páginas publicadas. GO-019 precede GO-020 no backlog e não depende dele — então o escopo aqui é o CICLO DO EDITOR (criar, salvar, reabrir, publicar, resolver conflito), não a renderização de uma página para um usuário final. Um novo pacote `internal/views` é criado com o mínimo necessário para esse ciclo: `_sc_views(id, name, table_id, template, min_role, configuration jsonb)` — `template` é armazenado como identificador de intenção (ex.: "List", "Show"), não interpretado por nenhuma lógica de renderização (que não existe ainda); `configuration` é o documento de layout que o builder Craft.js produz (`craftToSaltcorn`, já testado em GO-018).
3. **Controle de concorrência de views reaproveita exatamente o padrão de `internal/records` (GO-013): xmin/`_version`.** "Conflito de edição é apresentado sem sobrescrever silenciosamente" (critério de aceite) é a MESMA garantia que `UpdateRecord` já prova — reaproveitada, não reinventada, para `UpdateView`.
4. **"Publicar" é uma escrita de `min_role`, não um mecanismo novo.** Uma view nova nasce com `min_role = RoleAdmin` (piso seguro, "nada liberado por omissão", mesmo espírito de `metadata.TableOptions`); publicar = `UpdateView` baixando `min_role` (ex.: para `RolePublic`). "Publica com dois papéis" (critério de aceite) é testado assim: um ator admin cria/edita; antes de publicar, um ator público não consegue ler a view (403); depois de publicar, consegue.
5. **"Preview" já existe no builder Craft.js reaproveitado em GO-018** (`Builder.js` já tem um seletor de dispositivo de preview embutido) — não fabricado de novo aqui; `BuilderPanel.tsx` já expõe isso via o bundle existente, sem trabalho adicional.
6. **E2E via HTTP real, não navegador.** Confirmado em GO-018: não há ferramenta de browser/screenshot disponível neste ambiente. O "E2E" desta tarefa é um teste Go real (Postgres real, `httptest`, tokens `ServiceIdentity` reais assinados/verificados) que exercita a cadeia completa — criar tabela, criar view, salvar, reabrir, publicar com dois papéis, conflito de edição — via as rotas HTTP reais de `cmd/server`, o nível mais realista de "ponta a ponta" alcançável sem navegador. Documentado explicitamente como tal, não apresentado como um E2E de navegador que não ocorreu.
7. **BFF e frontend conectados ao fluxo real**, não só ao mock: `bffClient.ts` (frontend) ganha `createTable`/`addField`/`createView`/`getView`/`updateView`; o BFF (`app.ts`) ganha as rotas correspondentes, com a mesma disciplina de sessão/CSRF/Idempotency-Key já usada em GO-017. `BuilderPanel`/fluxo de editor no frontend passam a poder salvar/reabrir de verdade (não só o layout de mock de GO-018) — o mock continua existindo para os testes que não precisam de um BFF real, mesmo padrão de GO-018.

### Achado de verificação (regressão deliberada em três camadas)

Para provar que "conflito de edição é apresentado sem sobrescrever silenciosamente" realmente se sustenta em toda a pilha (não só numa camada isolada), a checagem de `_version`/xmin foi deliberadamente desabilitada e restaurada três vezes, uma por camada, confirmando falha genuína antes de restaurar:

1. **`internal/views/commands.go`** — removida a cláusula `AND xmin::text = $5` do `UPDATE` de `UpdateView`. `TestUpdateView_ConcurrentEditConflict` falhou (`UpdateView (sessão B, versão obsoleta) = <nil>, esperado ErrVersionConflict`). Restaurado, suíte volta a passar (7/7).
2. **Mesma alteração**, com apenas `TestEditorE2E_CreateTableViewSaveReopenPublish` rodando: falhou especificamente no passo 7 (`salvar com _version obsoleto: status = 200, ..., esperado 409`) — prova que a falha se propaga até a camada HTTP completa, não só o comando Go isolado. Restaurado, teste volta a passar.
3. **`migracao/packages/bff/test/mockGoServer.ts`** — a checagem `current._version !== body._version` do mock foi trocada por `if (false && current!._version !== body._version)` (o `!` foi necessário para satisfazer o estreitamento de fluxo do TypeScript em modo estrito após o curto-circuito `false &&`). Rodando a suíte do BFF, exatamente 1 teste falhou (`conflito de edição concorrente...`, em `editor.test.ts`). Restaurado (removidos o `false &&` e o `!`), suíte volta a 40/40.

Essa disciplina (desabilitar → confirmar falha real → restaurar → confirmar passe) já vinha sendo aplicada em tarefas anteriores desta migração; aqui foi repetida em três pontos distintos da pilha para a mesma garantia.

### Achado de escopo adicional (descoberto durante a implementação do frontend)

O botão "Next" do builder Craft.js (`packages/saltcorn-builder/src/components/Builder.js`) não expõe o documento editado via nenhum callback React — ele grava o JSON em `<input type="hidden">`s dentro de um `<form id="scbuildform">` e chama `.submit()` nativo (POST + reload de página inteira). Um `submit()` chamado programaticamente não dispara o evento `submit` (só `.requestSubmit()` dispara), então nem `onSubmit`/`preventDefault()` do React conseguem interceptá-lo — e o destino seria de qualquer forma um POST de formulário HTML, que o BFF (API JSON) não atende. Documentado em `migracao/packages/frontend/README.md` (seção "Achado de escopo") em vez de contornado com um hack (monkey-patch de `HTMLFormElement.prototype.submit`): `EditorPage.tsx` implementa e testa o ciclo completo salvar/reabrir/conflito/publicar contra o BFF real usando a `configuration` já conhecida pelo shell; extrair a edição AO VIVO de dentro do canvas Craft.js fica para GO-020 (runtime de views).
